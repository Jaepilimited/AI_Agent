2. Proxy — 접근 이력이 없는 것이 맞습니다
━━━━━━━━━━━━━

"접근 이력이 없다"는 회신이 저희 테스트 결과와
일치합니다. 저희 패킷이 Proxy 서버까지 도달하지
못하고 있어, Squid 입장에서는 남길 로그 자체가
없는 상황으로 보입니다.

▸ 테스트 결과 — 2회 실시, 동일 결과

 1차 : 2026-07-29 11:54~11:55 KST
 2차 : 2026-07-29 12:21~12:22 KST

 [WAS 10.1.150.5 / APP 10.1.150.105 / Web 10.1.100.5]
 → 10.1.50.5 (3대 모두 동일)
  · 3128 : 무응답 (timeout)
  · 443  : 무응답 (timeout)
  · 8080 : 무응답 (timeout)
  · ICMP : 무응답

▸ 판단 근거 1 — 무응답(timeout)이지 거부(refused)가 아님

 연결 거부라면 Proxy 서버까지는 패킷이 도달한 것이라
 로그에 흔적이 남을 수 있지만, 무응답은 중간 경로에서
 패킷이 폐기된 경우라 로그가 남지 않습니다.

▸ 판단 근거 2 — 동일 경로의 다른 목적지는 정상

 WAS 서버의 라우팅 테이블은 아래와 같습니다.

  default via 10.1.150.1 dev eth0
  10.1.150.0/24 dev eth0 (로컬)

 Proxy(10.1.50.5)와 DB(10.1.200.5)는 둘 다 로컬
 서브넷 밖이라 동일하게 게이트웨이 10.1.150.1을
 경유합니다. 그런데

  · 10.1.200.5:3306 (DB)    → 정상 연결
  · 10.1.50.5:3128 (Proxy)  → 무응답

 같은 경로·같은 게이트웨이인데 목적지에 따라 결과가
 갈립니다. 서버의 네트워크 설정이나 라우팅 문제가
 아니라, 목적지별 방화벽 정책 차이로 보입니다.

▸ 요청

 위 두 시각대(11:54~11:55, 12:21~12:22) 기준으로
 아래 구간의 방화벽 정책 및 차단 로그 확인을
 부탁드립니다.

  · WAS 10.1.150.5 → Proxy 10.1.50.5 : TCP 3128
  · APP 10.1.150.105 → Proxy 10.1.50.5 : TCP 3128

 참고로 설계서에는 WAS→Proxy 구간이 HTTPS(443)로
 기재되어 있는데, 안내해 주신 Squid 포트는 3128
 입니다. 정책이 443으로만 등록되어 있다면 이 부분이
 원인일 수 있습니다.

 저희 쪽에서 추가로 확인할 사항이 있으면
 말씀해 주시면 바로 테스트하겠습니다.
