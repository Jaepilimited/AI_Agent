# 로그인 개인 업무 브리핑 설계 (2026-08-25)

> 사용자가 로그인해 새 대화를 보는 순간, **오늘 받은 메일·오늘부터 7일 일정·기존 업무 지표
> 브리핑·우선 확인 3건**을 한 화면에 보여준다. Google Workspace에는 읽기만 한다.

## 결정 요약

- 첫 화면은 별도 대시보드 탭이 아니라 현재 채팅의 `chat-welcome` 안에 둔다.
- **기존 저장본을 먼저 보여주고 뒤에서 최신화**한다. 첫 렌더를 Google API나 LLM이 막지 않는다.
- 캘린더와 메일은 전용 경량 수집 함수로 Google API를 직접 조회한다. 로그인 때 범용 GWS 에이전트를
  돌리지 않는다.
- 캘린더·메일 건수·읽지 않음 여부는 결정적 코드가 만들고, Flash LLM은 메일 미리보기의 짧은
  요약과 `확인 후보` 문구만 만든다.
- 사용자가 고른 v1 범위는 **읽기 전용**이다. 메일 읽음 처리·회신·보관·일정 생성/수정은 하지 않는다.
- 모든 사용자 판정은 JWT의 `user.id`·`user.email`로 한다. 요청 파라미터로 받은 이메일은 믿지 않는다.
- 기존 `daily_briefings`의 개인화 매출 브리핑은 재사용하고 같은 내용을 다른 테이블에 복제하지 않는다.

## 목표와 성공 조건

지금 첫 화면은 이름과 질문 예시만 보여준다. 사용자가 무엇을 물을지 이미 알아야 가치가 생긴다.
새 첫 화면은 로그인한 사람이 **지금 무엇을 먼저 확인해야 하는지**를 질문 전에 보여주는 것이 목적이다.

성공 조건:

1. 캐시가 있으면 `/api/auth/me` 완료 후 **500ms 이내**에 저장된 개인 업무 브리핑이 나타난다
   (서버 응답 p95 목표, 브라우저·사내망 시간 제외).
2. Google 연결 사용자는 백그라운드 최신화 결과를 **15초 안에** 받는다. 15초를 넘기면 저장본 또는
   결정적 원본 목록으로 끝내고 화면을 계속 로딩 상태로 두지 않는다.
3. 메일·일정·기존 업무 브리핑 중 하나가 실패해도 나머지 카드가 보인다.
4. 메일 요약·우선 확인 항목의 모든 링크와 `source_id`는 실제 조회 결과에 존재한다.
5. 다른 사용자의 스냅샷·Google 연결 여부·토큰에 접근할 수 없다.
6. 이 기능 때문에 메일이나 캘린더 상태가 바뀌는 Google API 호출은 0건이다.

## 현재 재사용할 기반

| 기존 구성 | 재사용 방식 |
|---|---|
| `app/core/briefing.py` | `for_user(user.id)`의 최신 개인화 업무 지표 브리핑을 첫 화면 네 번째 카드로 사용. `for_date`도 함께 표시 |
| `app/core/google_auth.py` | 사용자별 OAuth 토큰과 `gmail.readonly`·`calendar.readonly` 범위 사용 |
| `app/core/google_workspace.py` | Gmail·Calendar 직접 조회 함수 재사용. 첫 화면 전용 경량 메타데이터 반환을 확장 |
| `app/agents/gws_agent.py` | 날짜 질의 규칙과 Flash REST 클라이언트 사용 경험을 재사용. 범용 분류·응답 생성 루프는 사용하지 않음 |
| `app/api/auth_api.py` | `/api/auth/me`가 확정한 사용자로 초기화를 시작 |
| `app/frontend/chat.html`, `chat.js` | 기존 `chat-welcome`과 Google 연결 버튼을 확장 |

`daily_briefings`는 매일 08:20 생성되며 이미 `user_id`로 격리되어 있다. 숫자와 문장은 코드가 만들고
LLM을 쓰지 않으므로, 첫 화면에서도 이 계약을 그대로 보존한다.

## 접근안 비교

### A. 혼합형 집계기 + 저장본 우선 표시 — 채택

서버가 Calendar와 Gmail을 직접 병렬 조회해 구조화된 스냅샷을 만들고, 첫 화면은 현재 날짜의 저장본을
즉시 그린 다음 비동기로 최신화한다.

- 장점: 첫 화면이 빠르고, 섹션별 실패 격리가 쉽고, 출력 계약을 테스트할 수 있다.
- 단점: 작은 캐시 테이블과 첫 화면 전용 집계 코드가 필요하다.
- 적합성: 로그인 화면처럼 항상 같은 모양과 제한된 지연이 필요한 경로에 가장 맞다.

### B. 로그인 때 기존 `GWSAgent.run("오늘 메일과 이번 주 일정")` 호출

- 장점: 새 수집 코드가 적다.
- 단점: 분류·텍스트 조립·LLM 포맷 전체를 매번 거쳐 느리고, 구조화된 카드 계약이 없으며,
  한 종류의 실패가 전체 답변 문자열에 섞인다. 범용 에이전트는 채팅 질문에는 맞지만 첫 화면 API에는
  맞지 않는다.

### C. 아침 배치에서만 전 사용자 브리핑 생성

- 장점: 로그인 응답은 가장 빠르다.
- 단점: 배치 이후 도착한 메일과 바뀐 일정이 반영되지 않고, 아침 배치 실패 시 하루 종일 낡는다.

따라서 A를 쓰되, 아침 선계산을 보조 수단으로 더한다. **배치가 단일 진실 공급자는 아니다.**

## 첫 화면 경험

새 대화 또는 로그인 직후의 빈 대화에서만 보인다. 기존 대화를 열었을 때 대화 위에 끼워 넣지 않는다.
로고를 눌러 홈으로 돌아오거나 `새 대화`를 누르면 다시 볼 수 있다.

데스크톱은 2열, 모바일은 1열이다.

1. 상단: `홍길동님, 오늘 브리핑입니다`와 마지막 갱신 시각
2. `오늘 우선 확인` — 최대 3건
3. `7일 일정` — 오늘 포함 7개 날짜로 묶은 일정
4. `오늘 메일` — 받은 메일 수·읽지 않은 수·핵심 요약·확인 후보
5. `업무 지표` — 기존 `daily_briefings` 최신 1건
6. 기존 질문 예시 칩과 채팅 입력창

카드의 상태는 `준비 중`, `최신`, `저장본`, `연결 필요`, `결과 없음`, `오류` 중 하나를 명시한다.
오래된 저장본을 최신인 것처럼 보여주지 않는다.

업무 지표는 매일 무조건 생기지 않는다. 기존 규칙이 `알릴 만한 변화가 있을 때만` 저장하기 때문이다.
최신 항목이 있으면 실제 `for_date`를 제목 옆에 표시하고, 오늘 새 항목이 없다는 사실과 과거 항목의
기준일을 섞지 않는다. 기존 `briefing_opt_out` 사용자는 이 카드를 다시 켤 수 있는 상태만 보고 옛 항목을
자동 노출하지 않는다.

### Google 미연결 사용자

메일·일정 영역을 숨기지 않는다. 두 카드 자리에 다음을 보여준다.

- `Google Workspace를 연결하면 오늘 메일과 7일 일정을 볼 수 있습니다.`
- 기존 상단 연결 동작을 재사용하는 `Google 연결` 버튼
- 업무 지표 브리핑과 기존 질문 예시는 그대로 표시

연결 팝업이 완료되면 페이지 새로고침 없이 상태를 다시 확인하고 첫 최신화를 실행한다.

### 항목 클릭

- 캘린더 일정: Google Calendar의 `htmlLink`를 새 탭으로 연다.
- 메일: Gmail 메시지 링크를 새 탭으로 연다.
- 업무 지표: 기존 `follow_up`을 채팅 입력창에 넣되 자동 전송하지 않는다.
- `자세히 물어보기`: 선택한 출처의 제목·보낸 사람을 포함한 GWS 질문을 입력창에 넣는다.

링크가 없는 항목은 클릭 가능한 모양으로 그리지 않는다.

## 시간과 조회 범위

모든 날짜 경계와 표시는 `Asia/Seoul`을 기준으로 한다.

### 7일 일정

- 범위: 오늘 00:00 이상, 오늘+7일 00:00 미만 — **오늘과 다음 6일**
- 기본 캘린더(`primary`)만 조회한다.
- 종일·여러 날 일정은 조회 구간과 겹치면 포함한다.
- 오늘 이미 끝난 일정은 숨기지 않고 흐리게 표시한다. 사용자가 오늘 한 일을 함께 볼 수 있다.
- 최대 50건을 받고, 화면은 날짜별로 묶어 스크롤한다. 50건을 넘으면 `50건 이상`이라고 밝힌다.

### 오늘 메일

- 범위: 오늘 00:00부터 현재까지 받은 메일
- 스팸·휴지통·임시보관·보낸 메일은 제외한다.
- 최근 20건의 헤더와 Gmail `snippet`만 요약 입력으로 사용한다.
- 본문·첨부파일은 첫 화면 자동 브리핑에서 내려받지 않는다. 자세한 본문 요약은 사용자가 채팅에서
  명시적으로 요청했을 때 기존 GWS 경로가 담당한다.
- 다음 페이지가 있으면 정확하지 않은 총건수를 만들지 않고 `20건 이상`으로 표시한다.
- 읽지 않음 수는 Gmail의 `UNREAD` 라벨로 코드가 센다.

## 응답 모델

`GET /api/personal-briefing`과 새로고침 응답은 같은 봉투를 사용한다.

```json
{
  "for_date": "2026-08-25",
  "timezone": "Asia/Seoul",
  "generated_at": "2026-08-25T08:31:12+09:00",
  "needs_refresh": true,
  "google": {
    "connected": true,
    "account": "user@skin1004korea.com"
  },
  "priorities": [
    {
      "source": "calendar",
      "source_id": "event-id",
      "title": "오전 10시 주간회의",
      "reason": "24시간 안에 시작",
      "url": "https://calendar.google.com/..."
    }
  ],
  "calendar": {
    "status": "stale",
    "items": [],
    "truncated": false,
    "error_code": ""
  },
  "mail": {
    "status": "ready",
    "count_label": "8건",
    "unread": 3,
    "summary": "결재 요청 1건과 일정 공유 2건이 있습니다.",
    "action_candidates": [],
    "items": [],
    "truncated": false,
    "error_code": ""
  },
  "business": {
    "status": "ready",
    "item": {
      "for_date": "2026-08-23",
      "title": "...",
      "body": "...",
      "follow_up": "..."
    }
  }
}
```

`status` 허용값은 `ready`, `stale`, `empty`, `disconnected`, `error`다. 프론트가 임의 문구를
추론하지 않고 이 값으로 상태를 그린다. `error_code`는 `oauth_missing`, `oauth_expired`,
`google_timeout`, `google_quota`, `summary_failed`처럼 제한된 코드만 내보내며 내부 예외 문자열은
사용자에게 보내지 않는다.

메일 `items`에는 `id`, `thread_id`, `subject`, `from_display`, `received_at`, `unread`, `url`만 둔다.
`snippet`과 본문은 응답·DB·로그에 넣지 않는다. 캘린더 `items`에는 `id`, `title`, `start`, `end`,
`all_day`, `location`, `url`, `ended`를 둔다.

## 서버 흐름

```text
로그인 → /api/auth/me
          ↓
GET /api/personal-briefing
  ├─ 기존 daily_briefings 최신 1건 결합
  ├─ 오늘 스냅샷 반환 또는 빈 섹션 반환
  └─ needs_refresh 계산
          ↓ 화면 즉시 렌더
needs_refresh=true 이면
POST /api/personal-briefing/refresh
  ├─ JWT user로 OAuth 자격 확인
  ├─ Calendar 조회 ─┐
  ├─ Gmail 조회 ────┼─ 병렬, 섹션별 타임아웃
  └─ 업무 브리핑 ───┘
          ↓
  메일 미리보기 Flash JSON 요약 1회
          ↓
  source_id 검증 → 우선 확인 최대 3건 → 저장 → 응답
          ↓
프론트 카드만 교체
```

### LLM의 제한된 역할

LLM은 메일 20건의 `subject`, `from`, `snippet`을 받아 다음 JSON만 만든다.

- 전체 요약 2문장 이하
- `action_candidates` 최대 3개: `message_id`, 짧은 이유

서버는 `message_id`가 실제 입력 집합에 없으면 해당 항목을 버린다. 제목·보낸 사람·시간·건수·읽지 않음
여부는 LLM 출력에서 받지 않고 원본 API 값만 쓴다. LLM 실패·타임아웃 시 메일 카드에는 최근 제목 목록과
결정적 건수만 보여준다. 이 경우 `summary_failed`를 표시하되 카드 전체를 실패시키지 않는다.

`오늘 우선 확인`은 다음 후보를 코드로 합친다.

1. 24시간 안에 시작하는 가장 가까운 일정
2. 검증을 통과한 메일 확인 후보
3. 오늘 사용할 수 있는 기존 업무 지표 브리핑

최대 3건이며 같은 출처로만 채우지 않는다. 이 목록은 `해야 할 일`이 아니라 **확인 추천**으로 표현한다.
Google 정보만으로 사용자의 실제 우선순위를 단정하지 않는다.

## API와 모듈 경계

새 구성:

- `app/core/personal_briefing.py`
  - 조회 범위 계산, Calendar/Gmail 수집, 구조 정규화, LLM 요약 검증, 우선 확인 조합
- `app/core/personal_briefing_store.py`
  - 사용자별 오늘 스냅샷 저장·조회·삭제·만료 정리
- `app/api/personal_briefing_api.py`
  - `GET /api/personal-briefing`
  - `POST /api/personal-briefing/refresh`
- `tests/test_personal_briefing.py`
- `tests/test_personal_briefing_api.py`

`google_workspace.py`에는 첫 화면 수집에 필요한 경량 함수만 추가한다. 기존 `search_gmail()`의 전체 본문
계약을 몰래 바꾸지 않는다.

### GET

- 부작용 없이 저장본과 기존 업무 브리핑을 읽는다.
- 오늘 스냅샷이 없거나 10분 이상 됐으면 `needs_refresh=true`다.
- 다른 날짜의 메일을 `오늘 메일`로 표시하지 않는다.

### POST refresh

- 사용자별 잠금으로 동시 Google 조회를 하나로 합친다.
- 10분 안에 성공한 최신본이 있으면 Google을 다시 호출하지 않고 그대로 반환한다.
- 각 Google 섹션 10초, LLM 8초, 전체 15초의 상한을 둔다.
- 한 섹션 실패 시 성공한 섹션만 새로 저장하고, 실패한 섹션은 같은 날짜의 저장본을 `stale`로 유지한다.
- 요청 본문이나 쿼리에 `user_id`·`user_email`을 받지 않는다.

## 캐시와 아침 선계산

MariaDB `personal_briefing_snapshots`를 사용자당 한 행으로 둔다.

| 컬럼 | 용도 |
|---|---|
| `user_id` PK | 소유자. 모든 조회·갱신 WHERE 조건의 첫 축 |
| `for_date` | 다른 날짜 스냅샷을 오늘 것으로 오인하지 않게 함 |
| `google_account_hash` | 연결 계정이 바뀌면 이전 스냅샷 무효화 |
| `calendar_json` | 정규화된 일정 메타데이터 |
| `mail_json` | 요약·제목·보낸 사람·링크. snippet·본문 없음 |
| `priorities_json` | 검증된 출처 참조만 저장 |
| `generated_at` | 최신 여부와 화면 표시 |
| `updated_at` | 운영 진단 |

사용자당 한 행을 덮어써 과거 메일·일정 기록을 축적하지 않는다. 매일 정리 작업도 `for_date < 오늘-1일`을
삭제해, 계정이 장기간 비활성인 경우 남은 옛 행을 제거한다. Google 연결 해제 시 해당 사용자 스냅샷도
즉시 삭제한다.

매일 08:30에 다음 사용자만 제한 동시성 3으로 선계산한다.

- 활성 사용자
- 퇴사 부서가 아님
- 최근 30일 안에 로그인
- Google 토큰 파일이 있음

선계산 실패는 로그인 요청을 막지 않는다. 로그인 후 POST 최신화가 같은 코드를 다시 사용한다. 스케줄러와
API가 서로 다른 구현을 가지지 않는다.

## OAuth와 개인정보 방어

현재 `/auth/google/status`, `/login`, `/revoke`는 `user_email` 쿼리를 받는다. 개인 브리핑을 붙이면서 이
값을 계속 신뢰하면 다른 사람의 연결 여부 조회·토큰 삭제가 가능하고, OAuth 상태도 이메일 평문이라 연결
대상이 바뀔 수 있다. 새 기능의 선행 조건으로 같은 변경에서 고친다.

- `/auth/google/login`, `/status`, `/revoke`는 `Depends(get_current_user)`의 이메일만 사용한다.
- OAuth `state`는 `user_id`, 내부 이메일, 발급시각, 무작위 nonce를 담은 **서명된 10분 만료 값**으로
  바꾼다. nonce 해시는 작은 `google_oauth_states` 테이블에 만료시각과 함께 두며 평문 state는 저장하지
  않는다.
- 콜백은 서명·만료·현재 로그인 사용자 일치·미사용 nonce를 검증하고, 같은 트랜잭션에서 nonce를
  사용 처리한 뒤에만 그 사용자 경로에 토큰을 저장한다. 완료·만료 행은 정리한다.
- 콜백 HTML의 사용자 이메일은 HTML escape한다.
- 토큰과 refresh token은 응답·로그·MariaDB에 넣지 않는다.
- 첫 화면 수집 로그에는 `user_id`, 섹션별 건수, 소요시간, 상태 코드만 남긴다. 메일 제목·보낸 사람·
  snippet·일정 제목은 로그에 남기지 않는다.
- 브라우저 `localStorage`에 메일·일정 스냅샷을 저장하지 않는다.

Google 계정이 내부 계정 이메일과 달라도 현재처럼 연결 계정을 화면에 명확히 표시한다. 토큰의 소유 키는
서명된 내부 사용자이고, Google 계정 이메일은 표시·캐시 무효화에만 쓴다.

## 오류·빈 결과 처리

| 상황 | 화면과 서버 동작 |
|---|---|
| Google 미연결 | 메일·일정 각각 `연결 필요`, 업무 지표는 정상 표시 |
| refresh token 만료/취소 | 저장본은 `저장본`으로 표시하고 재연결 버튼 제공 |
| Calendar만 실패 | 메일과 업무 지표는 갱신, 일정만 저장본 또는 오류 |
| Gmail만 실패 | 일정과 업무 지표는 갱신, 메일만 저장본 또는 오류 |
| LLM 요약 실패 | 건수와 최근 메일 목록은 표시, 요약만 `summary_failed` |
| 오늘 메일 0건 | `오늘 받은 메일이 없습니다`, 오류로 취급하지 않음 |
| 7일 일정 0건 | `앞으로 7일간 등록된 일정이 없습니다`, 오류로 취급하지 않음 |
| 업무 지표 변화 없음 | 기존 규칙대로 `새로 알릴 만한 업무 지표가 없습니다` |
| 오늘 캐시 없음 + Google 지연 | 카드별 skeleton 후 15초에 명시적 오류로 종료 |

예외 문자열과 Google 응답 본문을 그대로 사용자에게 노출하지 않는다.

## 프론트엔드 상태 관리

`chat.js:init()`에서 `/api/auth/me` 성공 뒤 다음을 시작한다.

1. 이벤트 리스너와 기존 채팅 초기화는 그대로 진행한다.
2. `loadPersonalBriefing()`은 대화 목록 로드와 병렬 실행한다.
3. GET 응답을 카드에 그린다.
4. `needs_refresh`면 POST를 백그라운드로 호출하고, 성공 시 해당 카드 DOM만 교체한다.
5. 사용자가 그 사이 기존 대화를 열면 refresh 결과를 웰컴 화면에만 보관하고 대화 화면을 덮지 않는다.
6. 새 대화로 돌아오면 최신 메모리 상태를 즉시 그린다.

렌더링은 `textContent` 또는 공용 escape 함수만 사용한다. 메일 제목·보낸 사람·일정 제목을 `innerHTML`에
그대로 넣지 않는다. 외부 URL은 `mail.google.com`, `calendar.google.com`, 그리고 Calendar API가 쓰는
`www.google.com/calendar/` 경로만 허용해 새 탭으로 연다.

## 테스트

### 단위 테스트

- KST 자정 경계, 오늘+6일 마지막 일정, 종일·여러 날·이미 끝난 오늘 일정
- 메일 0건, 20건, 21건 이상, 읽지 않음 라벨
- Gmail 본문·첨부파일을 첫 화면 수집이 요청하지 않는지
- LLM이 없는 `message_id`를 반환하면 버리는지
- LLM 실패 시 결정적 목록으로 폴백하는지
- 우선 확인 최대 3건·출처 다양화·실제 `source_id` 검증
- 오늘이 아닌 캐시를 오늘 메일로 반환하지 않는지
- 사용자별 잠금과 10분 TTL

### API·보안 테스트

- 인증 없는 GET/POST는 401
- 요청한 사용자와 다른 `user_id`/이메일을 주입할 입력면이 없음
- 사용자 A가 사용자 B의 스냅샷을 읽거나 갱신할 수 없음
- OAuth status/login/revoke가 JWT 사용자만 사용
- 변조·만료·재사용된 OAuth state 거부
- 연결 해제 시 토큰과 스냅샷 모두 삭제
- 메일·일정 내용이 캡처 로그에 나타나지 않음

### 프론트엔드·회귀 테스트

- 연결/미연결, 캐시 있음/없음, 부분 실패의 카드 상태
- 로그인 첫 화면과 새 대화에서는 보이고 기존 대화에는 끼지 않음
- refresh 도중 대화를 열어도 화면을 덮지 않음
- 모바일 1열, 긴 한국어·영문 메일 제목 말줄임과 hover/focus 전체 문구
- 키보드 포커스, 새 탭 링크의 `rel="noopener noreferrer"`
- 기존 `tests/test_briefing.py`, `tests/test_gws_gmail.py`, 인증·대화 테스트 전체 통과

## 이후 추가 후보

v1 사용 데이터를 보고 다음 순서로 판단한다.

1. **회의 준비 카드** — 24시간 내 회의의 관련 메일·문서를 사용자가 눌렀을 때만 찾아 요약
2. **일정 충돌·이동 시간 경고** — 겹치는 일정과 연속 회의 표시
3. **오래 안 읽은 중요 메일** — 오늘 메일이 아니라 3일 이상 미확인 후보를 별도 표시
4. **마감·후속조치 추적** — 사용자가 명시적으로 등록한 할 일만 관리
5. **브리핑 선호 설정** — 카드 숨김, 선계산 시간, 메일 범위 조정

자동 회신이나 자동 일정 변경은 이 후보 목록에도 넣지 않는다. 쓰기 기능은 별도의 권한·승인·감사 설계가
필요한 독립 프로젝트다.
