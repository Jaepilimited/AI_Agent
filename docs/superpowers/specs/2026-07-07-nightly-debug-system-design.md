# 야간 자동 디버깅·개선 시스템 설계

**Date**: 2026-07-07
**Status**: Approved
**Scope**: 퇴근 시간대(22:00~07:00) 동안 2시간 간격으로 서버 로그·코드 변경분을 점검하여 문제를 찾고, 저위험 수정은 자동 적용, 그 외는 리포트만 남기는 무인 시스템

---

## 문제 정의

현재 `scripts/server_watchdog.py`는 PM2 프로세스/포트 생사만 감시하고 30초마다 자동 복구한다 — 인프라 레벨 가용성 문제만 다룬다. 코드 로직 버그, 런타임 예외, 잠재적 리스크는 사람이 직접 로그를 보거나 리뷰를 요청해야만 발견된다.

사용자가 퇴근한 이후에는 이런 문제가 다음 출근 때까지 방치된다. 오늘 세션에서 `.multiagent` 시스템 + `codex exec` CLI 폴백으로 실제 SQL 에이전트 보안 버그를 발견·수정 설계·adversarial 재검증까지 성공적으로 수행한 패턴이 있으므로, 이를 무인 반복 실행 가능한 형태로 스크립트화한다.

---

## 목표

- 서버 로그의 실제 에러/예외를 주기적으로 분석해 원인과 수정안을 제시한다.
- 마지막 실행 이후 변경된 코드 파일을 정적으로 리뷰해 잠재적 버그를 찾는다.
- 저위험 수정은 사람 개입 없이 커밋 + 프로덕션 재시작까지 자동 적용한다.
- SQL·인증·권한 로직 등 고위험 영역은 **코드로 하드코딩된 규칙**에 의해 항상 자동 적용에서 제외되고 리포트만 남는다.
- 자동 적용 직후 헬스체크로 실패를 감지하면 자동으로 롤백한다.
- 매 회차 결과를 로컬 파일 + 노션에 남겨 다음날 아침 확인할 수 있게 한다.

## 비목표

- SQL/인증/권한 로직의 자동 수정 (항상 사람 검토 필요 — 오늘 sql_agent.py 사례처럼 adversarial 검증에서도 완전히 못 걸러낼 수 있는 영역)
- 여러 파일에 걸친 리팩터링이나 기능 추가 (버그 픽스만 대상)
- 실시간/이벤트 트리거 (이번 스코프는 고정 스케줄만 — 에러 급증 감지 트리거는 향후 확장 후보)

## 전체 아키텍처

```
Windows Task Scheduler: "SKIN1004-Nightly-Debug"
  트리거: 22:00 시작, 2시간 간격 반복, 9시간 동안 (07:00까지 종료) — 1회 등록으로 ~5회/밤 실행
       │
       ▼
scripts/nightly_debug.py
  │
  ├─ 1) 상태 로드 — scripts/_nightly_state.json
  │     { last_run_at, last_git_commit, last_log_offset }
  │     (파일 없으면 첫 실행으로 간주, 최근 2시간만 스캔)
  │
  ├─ 2) 수집 (결정적 코드, LLM 미사용)
  │     ├─ pm2 에러 로그(logs/pm2-prod-error.log)에서 last_log_offset 이후 새 에러/트레이스백 파싱
  │     │    "에러"로 카운트하는 기준: (a) structlog JSON 라인의 "level":"error"/"critical",
  │     │    (b) "Traceback (most recent call last):"로 시작하는 멀티라인 블록.
  │     │    INFO/WARNING 레벨(예: notion_warmup_fetch_failed)은 제외 — 기존에 알려진 정상 warning 노이즈.
  │     └─ git diff --name-only <last_git_commit>..HEAD  (변경 파일 목록)
  │
  ├─ 3) 이슈 없음 → 상태만 갱신하고 조용히 종료 (리포트 생성 안 함 — 매일 밤 "이상없음" 노이즈 방지)
  │
  ├─ 4) 이슈별 분석 파이프라인 (아래 참조) — 로그 에러 1건, 변경 파일 1건 단위로 독립 실행
  │
  ├─ 5) 리스크 게이트 통과 항목만 자동 적용 → 헬스체크 → 실패 시 자동 롤백
  │
  └─ 6) 리포트 생성 → logs/nightly_debug/<날짜_시각>.md 저장 + 노션 업로드
```

오케스트레이션(무엇을 언제·어떻게 할지, 자동 적용 여부)은 전부 결정적 Python 코드가 담당한다. LLM(`codex exec`)은 "이 에러/diff를 분석하고 수정안을 제안"하는 좁은 역할만 수행하며, 자동 적용 여부를 스스로 판단하지 않는다.

---

## 이슈별 분석 파이프라인

각 이슈(로그 에러 1건, 또는 diff 파일 1건)마다 다음을 거친다:

```
이슈 발견
  │
  ├─ 1차 분석: codex exec -s read-only -
  │     입력: 에러 트레이스백/diff + 관련 코드 경로
  │     출력: 원인 설명 + 수정 diff 제안 (오늘 result.md 패턴과 동일한 스타일)
  │
  ├─ 리스크 분류 (코드 규칙, LLM 판단 아님 — 아래 "리스크 게이트" 참조)
  │     └─ 하드 제외 대상 → 2차 검증 생략, 바로 "보고만" 큐 (비용 절감)
  │
  ├─ 자동 적용 후보만: 2차 adversarial 검증 — codex exec -s read-only - (별도 프롬프트)
  │     "1차 수정안을 반박해봐라, 실제 코드와 직접 대조해서 재검증"
  │     STILL RISK/INCOMPLETE 판정 시 → 자동 적용 취소, "보고만" 큐로 강등
  │
  └─ 검증 통과 → 자동 적용 큐에 추가
```

- 각 이슈는 서로 독립적으로 파이프라인을 통과한다 (한 이슈의 결과가 다른 이슈에 영향 없음).
- `codex exec` 호출은 `subprocess`로 실행하고, stdout에서 최종 답변만 파싱한다 (긴 트레이스 출력 중 `tokens used` 직전 블록 추출 — 오늘 실제로 겪은 파싱 패턴을 그대로 재사용).
- codex 호출 자체가 타임아웃(5분)이나 에러로 실패하면 해당 이슈는 자동으로 "보고만" 큐로 내려간다.

## 리스크 게이트 (자동 적용 여부 — 전부 코드로 하드코딩)

수정안이 아래 조건을 **전부** 만족해야 자동 적용 후보가 된다. 하나라도 어기면 무조건 "보고만":

```python
# 파일 경로 하드 제외 — 내용과 무관하게 무조건 제외
DENYLIST_PATTERNS = [
    "app/agents/sql_agent.py",
    "app/core/security.py",
    "app/api/auth_api.py",
    "app/api/admin_api.py",
    "app/api/admin_group_api.py",
    "app/db/mariadb.py",
    "*.sql",
    "prompts/sql_generator.txt",
]
```

그 외 모든 조건:
- 수정 diff가 파일 1개만 변경 (여러 파일에 걸치면 자동 제외)
- 변경 줄 수 30줄 이내
- 새 import·새 함수·새 클래스 정의 없음 (기존 함수 내부 수정만 — 순수 버그 픽스 형태인지 AST로 확인)
- 2차 adversarial 검증에서 명시적으로 "SAFE"/"RESOLVED" 판정
- `ast.parse()`로 수정 후 파일이 syntax-valid한지 코드가 직접 확인 (LLM 주장 신뢰 안 함 — 오늘 세션에서 반복한 검증 패턴)

`DENYLIST_PATTERNS`는 처음엔 보수적으로 시작하고, 스크립트 스스로 이 목록을 넓히지 않는다 — 범위 확장은 항상 사람이 파일을 직접 수정해서 결정한다.

### 자동 적용 실행 순서

```
1. git commit (수정 diff, 메시지: "[nightly-auto-fix] <한 줄 요약>")
2. pm2 restart skin1004-prod
3. 30~60초 대기 → GET /health 확인 + 재시작 이후 에러 로그에 새 에러 없는지 확인
4. 실패 시 → git revert (직전 커밋) → pm2 restart (원복)
     → 이 건은 "자동 적용 시도했으나 롤백됨"으로 리포트에 기록
5. 성공 시 → "자동 적용 완료"로 리포트에 기록
```

## 리포트 형식

로컬 파일 (`logs/nightly_debug/<YYYY-MM-DD>_<HHMM>.md`) + 노션 업로드(`scripts/upload_to_notion.py` 기존 패턴 재사용):

```markdown
# 야간 점검 리포트 — 2026-07-08 22:00

## 자동적용됨 (N건)
- [파일:줄] 문제 요약 — 커밋 <hash>, 헬스체크 통과/롤백 여부

## 보고만 (N건)
- [파일] 문제 요약
  원인: ...
  제안 diff: ...
  자동적용 제외 사유: (데널리스트 파일 / diff 크기 초과 / 2차 검증 실패 / 여러 파일 걸침 등)

## 발견된 문제 없음
(해당 없으면 이 섹션 자체를 생략)
```

이슈가 하나도 없으면 리포트 파일 자체를 만들지 않는다 (매일 밤 "이상없음" 노이즈 방지).

## 스케줄링

기존 `SKIN1004-AD-Sync-Daily`(Task Scheduler, 매일 22:00)와 동일한 등록 방식으로 `SKIN1004-Nightly-Debug` 작업을 생성한다:
- 트리거: 매일 22:00 시작
- 반복: 2시간 간격
- 반복 기간: 9시간 (07:00 종료)
- 이 방식으로 트리거 1개만 등록하면 되고, 5개의 개별 트리거를 만들 필요가 없다.

## 예외 처리 원칙

- `codex exec` 호출이 5분 이상 걸리면 → 해당 이슈만 실패 처리, 스크립트 자체는 계속 진행
- 실행 시점에 이미 uncommitted 변경사항이 있으면(사람이 작업 중) → 이번 회차는 자동 적용 전부 스킵, "사용자가 작업 중이라 보고만 수행" 기록
- 스크립트 자체가 예외로 죽으면 → 다음 회차(2시간 후)에 이어서 실행. `server_watchdog.py`와는 완전히 별개 프로세스라 서로 간섭하지 않는다.

## 테스트 계획

1. `--dry-run` 플래그로 자동 적용(git commit/pm2 restart) 없이 리포트만 생성하는 모드를 먼저 구현한다.
2. 며칠간 `--dry-run`으로 실제 스케줄에 맞춰 돌려보고, 리스크 게이트가 예상대로 걸러내는지(자동 적용 후보 vs 보고만 분류가 타당한지) 리포트로 확인한다.
3. 문제 없으면 자동 적용을 실제로 켠다 (`--dry-run` 플래그 제거).
4. 최초 실 가동 후 며칠은 아침마다 리포트를 사람이 직접 대조 확인한다 (자동 적용된 커밋이 실제로 안전했는지 사후 검증).

## 후속 확장 후보 (이번 스코프 아님)

- 에러 급증 감지 시 즉시 트리거 (고정 스케줄 외 이벤트 기반 실행)
- `DENYLIST_PATTERNS`를 파일이 아니라 함수/라인 단위로 더 세밀화
- 자동 적용된 커밋에 대한 주간 회고(예: `retro` 스킬과 연계)
