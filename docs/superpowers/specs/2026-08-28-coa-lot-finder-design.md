# 공유드라이브 인증서류(COA·MSDS) 롯트 일괄 찾기 — 설계

**작성일**: 2026-08-28 · **상태**: 승인 대기 → 구현 예정
**요청**: 제품별 MSDS/COA를 롯트 단위로 하나씩 검색·다운로드하던 수작업을,
목록을 올리면 일치하는 파일을 찾아 경로/다운로드까지 주도록 자동화

---

## 왜 만드나

지금은 사람이 롯트 하나마다 드라이브를 검색하고, 맞는 파일인지 눈으로 확인하고,
받아서 전달한다. 목록이 수십 건이면 그만큼 반복된다.

셀라에 드라이브 검색이 이미 있지만 **이 용도로는 쓸 수 없다.** 실측으로 확인한 네 가지:

| 제약 | 근거 |
|---|---|
| 공유드라이브가 검색 대상에서 빠져 있다 | `search_drive()` (`app/core/google_workspace.py:325`) 의 `files().list()` 에 `includeItemsFromAllDrives`·`supportsAllDrives`·`corpora` 가 없다 |
| 한 번에 1건, 최대 10건 | `max_results=10` 고정, 목록 개념 없음 |
| 채팅 첨부가 이미지 전용 | `chat.html:195` `accept="image/png,image/jpeg,image/gif,image/webp"` |
| 다운로드 없음 | `webViewLink` 만 돌려준다 |

그리고 **가장 위험한 것**: 현재 드라이브 검색은 0건이면 `expand()`·`llm_variants()` 로
검색어를 넓혀 다시 찾는다. 롯트 검색에서 이건 오답 생성기다 (아래 참조).

## 실측 — 드라이브에 실제로 무엇이 있나 (2026-08-27 확인)

**롯트 검색은 실제로 통한다.** 롯트 `E08Z011` 로 검색하니 정확히 1건이 나왔다:
`51082SEA-003H SKIN1004 MADAGASCAR CENTELLA TEA-TRICA RELIEF AMPOULE COA (E08Z011)`

**다만 명명 규칙이 통일돼 있지 않다.**

| 형태 | 실제 파일명 |
|---|---|
| 롯트가 앞 괄호 + 뒤 반복 | `COA(DE001)(Full)_…SOOTHING SUN MILK 50ml_DE001_12,600EA.pdf` |
| 롯트가 뒤 괄호 | `51082SEA-001W …POREMIZING FRESH AMPOULE COA (E07Z082)` |
| 롯트에 공백 + 접미 1글자 | `COA_…PROBIO-CICA Glow SUN AMPOULE 50ml(N3)_F14D40 D` |
| 앞에 오더번호, `CoA` 대소문자 혼재 | `LO1048_(EN)CoA_…RETINOL 0.2 BOOSTING SHOT AMPOULE 30mL` |
| 롯트 없음 | `COA_SKIN1004 MADAGASCAR CENTELLA AMPOULE 100ml` |
| 중복본 | `…COA (SKMC) 416006.pdf의 사본` · 같은 파일이 두 폴더에 각각 |

**MSDS 는 롯트가 없다.** 제품·제작물 단위다:
`[CNS글로벌]1004DAY 키링 파우치(2026)_MSDS.pdf` · `Bio micro cell _Msds. En_WM.pdf`
→ 롯트로 MSDS 를 찾을 수 없다. **SKU·제품명으로 찾아야 한다.**

**PDF 본문 검색도 작동한다** (`fullText contains 'Certificate of Analysis'` 로 COA 본문이 잡혔다).
이번 범위에서는 쓰지 않지만, 나중에 넓힐 여지로 기록해 둔다.

### Drive 의 `contains` 는 토큰 앞부분 매칭이다 (2026-08-28 실측)

임의 부분문자열 매칭이 아니다. 구분자(`_`·`(`·공백·`-`)로 쪼갠 **토큰의 앞부분**에만 걸린다.

| 질의 | 결과 | 뜻 |
|---|---|---|
| `FE161` | 1건 — `COA_10116720_…SUN SERUM_FE161_15643EA` | 언더바 사이에 낀 롯트도 잡힌다 |
| `416022` | **0건** | 드라이브엔 `…COA (SKMC) 416006` 뿐 — 진짜 없는 롯트다 |

`416022` 는 목록의 EUSKC017(Cream 75ml) 이다. **넓혀 찾았다면 `416006` 을 정답으로 줬을 것이다.**
넓히기 금지의 실증 사례이므로 픽스처에 넣는다.

### 이 기능 최악의 실패 — 실물로 확인됨

사용자가 준 목록에 `EUSKA032 · Poremizing Fresh Ampoule 50ml · LOT E07Z083` 이 있다.
드라이브에는 **같은 제품의 `E07Z082`** COA 가 있다. 한 글자 차이의 **다른 롯트**다.

검색어를 넓히면 이것이 정답으로 나간다. COA 는 규제·고객 대응 문서라 그대로 밖으로 나간다.
**넓혀 찾기를 끄는 것이 이 설계의 전부다.**

## 결정 사항 (2026-08-28 사용자 확정)

| 항목 | 결정 |
|---|---|
| 검색 범위 | **공유드라이브 전체** |
| 접근 주체 | **사용자 본인 구글 계정** (OAuth `drive.readonly`) |
| 매칭 규칙 | **롯트 정확 매칭만** |
| 붙일 자리 | **전용 페이지** |
| 범위 | 목록 붙여넣기 + 엑셀 업로드 + 결과 표 + ZIP 일괄 다운로드 |

### 검색 전략 — 조회 시점 실시간 (채택)

롯트 N건을 각각 Drive API 로 검색한다 (병렬). 100건에 약 5초.

⛔ **파일명 색인을 DB 에 적재하지 않는다.** 두 가지가 깨진다:
색인은 누군가 **한 사람의 권한**으로 만들어지므로 "본인 권한으로 읽는다"는 결정과 충돌하고,
어제 올라온 COA 가 오늘 "없음" 으로 나온다. 규제 문서에서 없는 것을 없다고 잘못 말하는 것은
틀린 파일을 주는 것 다음으로 나쁘다.

OP 재고(`app/core/inventory.py`)에서 "조회할 때마다 시트를 직접 읽는다" 로 정한 것과 같은 이유다.
지연이 실제로 문제가 되면 그때 하이브리드(색인으로 후보를 좁히고 실시간 확인)를 검토한다.

## 구조

```
app/core/coa_finder.py      판정 — 순수 함수. LLM 없음. 파일 선택은 규칙이 한다
app/api/coa_finder_api.py   엔드포인트 — 검색(SSE) · ZIP 다운로드
app/static/coa_finder.html  전용 페이지
tests/test_coa_finder.py    회귀
```

`app/core/google_workspace.py` 의 `search_drive()` 에 공유드라이브 파라미터를 추가한다
(기존 드라이브 검색도 함께 고쳐진다 — 지금은 공유드라이브가 통째로 안 보인다).

### 단위와 경계

- `coa_finder.parse_list(text | xlsx_bytes) -> list[Row]` — 입력을 행으로. 조회하지 않는다
- `coa_finder.classify(lot, files) -> Verdict` — 검색 결과를 판정으로. **조회하지 않는다**
- `coa_finder.search_lots(creds, rows) -> Iterator[Result]` — 위 둘을 드라이브에 연결
- 판정 로직이 조회와 분리돼 있어야 회귀 테스트가 네트워크 없이 돈다

## 매칭 판정

롯트별로 `title contains '<롯트>'` 로 검색하고 결과를 네 갈래로 나눈다.

**"정확 매칭" 의 뜻** — 롯트 문자열이 파일명에 **그대로** 들어 있는 것만 받는다.
Drive 의 `contains` 가 토큰 앞부분 매칭이라(위 실측) 이것으로 충분하다.
정확 매칭이 아닌 것은 **넓히지 않는다**는 뜻이지, 파일명 전체가 롯트와 같아야 한다는 뜻이 아니다.

| 판정 | 조건 | 화면 |
|---|---|---|
| `찾음` | 정확히 1건 | 파일명 + 링크 |
| `여러건` | 2건 이상 | **전부** 나열, 사람이 고른다 |
| `없음` | 0건 | `없음` — 빈 칸으로 두지 않는다 |
| `확인필요` | 아래 두 경우 | 왜 그런지 함께 적는다 |

**`확인필요` 로 두는 두 경우**

1. **공백+접미 롯트** — `F31C28 D` 를 물었는데 접미 없는 `F31C28` 파일만 잡힌 경우.
   같은 것일 수도 아닐 수도 있다 — 어느 쪽으로 잡혔는지 밝히고 사람에게 넘긴다
2. **아주 짧은 롯트** — 4자 이하. 토큰 앞부분 매칭이라 다른 코드의 머리에 걸릴 수 있다

⚠️ **"6자리 숫자 롯트는 무조건 확인필요" 로 두지 않는다.** 처음엔 그렇게 잡았는데
실측(`416022` → 0건, `FE161` → 정확히 1건)에서 오매칭이 나지 않았다. Drive 가 토큰
앞부분만 보기 때문이다. 근거 없이 확인필요를 붙이면 **매일 같은 경고와 같은 종류의 소음**이 되고,
그러면 진짜 확인필요를 아무도 안 본다.

**세 가지를 못 박는다**

- ⛔ **넓혀 찾지 않는다.** 이 경로에서는 `expand()`·`llm_variants()` 를 부르지 않는다.
  `E07Z083` 을 물었는데 `E07Z082` 를 주는 것이 이 기능 최악의 실패다
- ⛔ **중복본을 접는다.** `…의 사본` 과 같은 파일이 두 폴더에 있는 경우가 실제로 있다.
  사본 표기를 뗀 이름 + 파일 크기가 같으면 같은 파일로 보고 **대표 1건만** 보여준다.
  내용이 같으므로 어느 쪽을 열어도 같다 — 사본을 다 나열하면 `여러건` 으로 잘못 보인다
- ⛔ **MSDS 는 COA 와 다른 열에 놓는다.** MSDS 는 롯트가 없어 SKU·제품명으로 찾는다.
  같은 열에 섞으면 롯트가 맞는 문서인 것처럼 보인다

## 화면 — `/coa-finder`

로그인 필요. 사이드바에서 진입. 구글 미연결 사용자에게는 표 대신 연결 버튼을 보여준다.

**입력 두 가지**
- 엑셀에서 복사 → 붙여넣기 (탭 구분 텍스트)
- `.xlsx` 업로드 (`openpyxl==3.1.5`, 이미 requirements 에 있다)

**열 인식은 헤더 낱말로 한다** — `SKU`/`품목`, `DESCRIPTION`/`제품명`, `LOT`/`롯트`.
⛔ 헤더를 몇 번째 행이라고 박지 않는다. 안내문 한 줄이 늘어나면 어긋나고,
그때 나는 것은 에러가 아니라 **0건**이다 (OP 재고 적재에서 실제로 겪은 함정).

**결과 표**

| SKU | 제품명 | 롯트 | COA | MSDS | 선택 |
|---|---|---|---|---|---|
| EUSKA022 | …Ampoule 100ml | FE103C | 찾음 · 링크 | 찾음 · 링크 | 체크 |
| EUSKC017 | …Cream 75ml | 416022 | **없음** (드라이브엔 416006 뿐) | 없음 | — |
| EUSKA024 | …Tone Brightening 100ml | F31C28 D | 확인필요 · 접미 없는 파일만 | 없음 | 체크 |

맨 위에 요약 한 줄 — `40건 중 COA 31건 · 없음 5건 · 확인필요 4건`.

**진행률을 SSE 로 흘린다.** 40~100건이 몇 초 걸리는데 다 끝날 때까지 빈 화면이면 멈춘 것으로 보인다.

**스타일**: `style.css` 의 기존 토큰만 쓴다 (`--bg-surface`·`--border`·`--text-muted`…).
⛔ 자바스크립트 안에 인라인 스타일을 두지 않는다 — 테마 전환에서 조용히 빠진다
(피드백 모달이 없는 변수 `--panel` 을 써서 라이트 모드에서 안 보이던 그 결함).
`chat.html` 의 캐시 버전과 CLAUDE.md 의 캐시 버전 줄을 함께 올린다.

## 다운로드

선택한 행의 파일을 **사용자 OAuth 토큰으로** `files().get_media(supportsAllDrives=True)` 받아
ZIP 으로 **스트리밍**한다. 서버 디스크에 남기지 않는다.

- ZIP 안 파일명은 `<SKU>_<롯트>_<원본파일명>` — 열어보지 않아도 어느 롯트 것인지 안다
- 상한 **200건 / 500MB**. 넘으면 거부하고 **몇 건이 넘었는지 밝힌다**
- ⛔ 받다가 실패한 파일은 ZIP 안에 `_받지못한_목록.txt` 로 넣는다. 조용히 빠지면 아무도 모른다
- ⛔ `ThreadPoolExecutor` 를 `with` 로 감싸지 않는다 — `shutdown(wait=False)` (프로젝트 규칙)

## 오류 처리

| 상황 | 처리 |
|---|---|
| 구글 미연결 / 토큰 만료 | 표 대신 연결 안내. **"전부 없음" 으로 보이면 안 된다** |
| 드라이브 API 오류 | 그 행만 `조회실패` 로 두고 나머지는 진행. 실패 건수를 요약에 적는다 |
| 목록에서 열을 못 찾음 | 어떤 헤더를 찾았고 무엇이 없는지 알려준다. 추측해서 진행하지 않는다 |
| 롯트 칸이 비어 있음 | COA 는 `롯트없음`, MSDS 는 제품명으로 계속 진행 |

## 테스트 (`tests/test_coa_finder.py`)

조회도 LLM 도 없는 순수 함수 검사가 대부분이라 빠르다.

**핵심 회귀 — 이 기능이 존재할 수 있는 조건**

```
E07Z083 을 물었을 때 E07Z082 파일이 결과에 들어오면 실패
416022 를 물었을 때 416006 파일이 결과에 들어오면 실패
```

둘 다 목록·드라이브에 **실재하는 값**이다. 넓히기를 되살리면 이 두 개가 먼저 깨진다.

그 외:
- 헤더 인식 — 헤더가 1행/3행/7행에 있어도 찾는다
- 판정 4갈래
- `FE161` — 언더바 사이에 낀 롯트가 `찾음` 으로 잡힌다
- `F31C28 D` — 접미 있는 파일과 없는 파일 각각의 판정
- 중복본 접기 (`…의 사본`, 같은 이름 다른 폴더)
- MSDS 가 COA 열에 섞이지 않는다

**픽스처**는 요청자가 준 실제 40행을 그대로 쓴다 (SKU / DESCRIPTION / LOT).

**조용한 실패 검사**(`tests/test_no_silent_failures.py`)에 추가: 캐시 버전 일치, CSS 변수 존재.

**자가 점검**(`app/core/self_check.py`)에 드라이브 접근 생존 검사 1종.
토큰이 만료되면 이 기능은 에러가 아니라 **"전부 없음"** 으로 보인다 — 조용한 실패다.

## 먼저 확인할 가정

⚠️ **사용자 OAuth(`drive.readonly`)로 공유드라이브가 실제로 보이는지 아직 실측하지 않았다.**
스코프는 맞지만 해당 공유드라이브에 그 사람이 멤버가 아니면 안 보인다.
**구현 첫 단계에서 이것부터 찔러본다.** 여기서 막히면 나머지 설계가 의미가 없다
(막히면 서비스계정을 공유드라이브 멤버로 넣는 쪽으로 접근 주체를 다시 논의한다).

⚠️ 네트워크 전제는 문서를 믿지 말고 찔러 볼 것 — WAS 의 프록시 허용 범위가
`www.googleapis.com` 에 대해 열려 있다는 것은 브리핑(Gmail·Calendar)이 도는 것으로
간접 확인되지만, Drive `get_media` 대용량 다운로드는 따로 확인한다.

## 범위 밖 (지금 하지 않는다)

- PDF 본문(fullText) 검색 — 파일명에 롯트가 없는 건까지 넓히는 것. 느리고 스캔본은 못 찾는다
