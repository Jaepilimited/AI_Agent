# PR 이슈 · 수상/랭킹 적재 — 두 시트, 두 가지 방식

**작성** 2026-09-07 · **상태** 설계 승인됨, 구현 대기
**계기** 사용자 요청 — 프레인 PR 시트의 `리스트` 탭과 수상/랭킹 시트를 셀라가 답하게 한다

---

## 1. 왜

셀라는 지금 매출·광고·물류·재고·사내문서에 답한다. **브랜드가 밖에서 무엇을 했고
무엇을 받았는지**는 답하지 못한다. 두 시트가 그 공백을 정확히 덮는다.

| 시트 | 탭 | 무엇 |
|---|---|---|
| `[스킨1004] 프레인 PR 이슈 전달` (`1MLuwW…`) | **리스트** | 월별 PR 이슈 — 신제품 출시·행사·실적·입점 확장·회사 관련 |
| `[SK/CL] 스킨1004 수상 및 랭킹 정보 취합` (`1oxtCp…`) | **수상및랭킹** | 수상·랭킹·설문 이력 + 마케팅 활용 권리 |

## 2. ⛔ 두 소스를 **다른 방식**으로 넣는다

요청은 "PR 같은 시스템으로" 였으나, 실측해 보니 두 데이터의 성격이 반대였다.
같은 방식으로 넣으면 한쪽이 조용히 틀린다.

| | PR 리스트 | 수상/랭킹 |
|---|---|---|
| 한 행의 모양 | **긴 서술문** (행사 진행 방식 수백 자) | **정형 표** (19열, 값이 짧고 균일) |
| 핵심 | 무슨 일이 있었나 | **숫자(순위)와 판정(활용 가능 여부)** |
| 방식 | **Qdrant 벡터** | **MariaDB 표 + 조회** |

**수상/랭킹을 벡터로 넣으면 안 되는 이유 (실측):**

1. `랭킹/점수` 가 숫자다 — `1` 이 63건, `2` 20건. *"화해 어워드 1위 제품"* 은 본질적으로
   필터·정렬이고, 임베딩은 `1` 과 `10` 을 구분하지 못한다. OP 재고를 벡터로 넣지 않기로
   한 근거(`104` 와 `1,040`)가 그대로 적용된다.
2. `가능 여부` 가 **법적 판단**이다 — `O 123 · △ 65 · X 5 · 논의중 4 · 빈칸 9`.
   못 쓰는 수상을 "쓸 수 있다" 고 답하면 실제 문제가 된다. 초상권을 LLM 없는 전용
   경로로 뺀 것, COA 찾기가 *"틀린 걸 주는 게 못 찾는 것보다 나쁘다"* 를 못 박은 것과
   같은 계열이다.
3. 206행뿐이라 표로 넣는 비용이 거의 없다.

## 3. 1단계 — 수상/랭킹 (표)

**권한이 이미 열려 있어 먼저 완성한다.** (`skin1004@skin1004-319714.iam.gserviceaccount.com`
접근 확인)

### 3.1 실측 (2026-09-07)

206 본문행 · 19열 · 2019~2026.

| 열 | 값 |
|---|---|
| `구분` | 랭킹 94 · 설문 60 · 수상 52 |
| `브랜드` | 스킨1004 190 · 좀비뷰티 12 · 커먼랩스 4 |
| `주최사` | 29종 (화해 84 · 쇼피 45 · 한국소비자포럼 14 · 글로우픽 7 · PICKY 7) |
| `획득 국가` | 11종 (대한민국 107 · 글로벌 39 · 인도네시아 15 · 필리핀 13) |
| `랭킹/점수` | 41종 — `1` 63 · `2` 20 · `-` 10 · `97%` 9 |
| `유/무료` | 무료 102 · 유료 95 · 빈칸 9 |
| `가능 여부` | O 123 · △ 65 · X 5 · 논의중 4 · 빈칸 9 |
| 수상 일자 | 미기재(`-`) 68건 |

### 3.2 저장

MariaDB `awards_rankings` (OP 재고와 같은 계열). 매일 1회 `awards_sync_daily`.

원문 열은 그대로 싣고, 파생은 **따로** 둔다:

```
category  brand  organizer  title
award_start  award_end  award_date          -- 수상 기간·일자
country  product  detail
rank_raw     rank_value                     -- 원문 / 파싱된 정수(가능할 때만)
paid  amount_raw
usage_flag   usage_start  usage_end  usage_region  usage_note
source_url  synced_at
```

### 3.3 ⛔ 조용히 틀릴 자리 넷

1. **헤더는 6번째 행에 있다** (위 5줄은 안내문·병합 헤더). 숫자로 박지 말고
   `구분` 이 있는 행을 찾는다. 어긋나면 에러가 아니라 **0건**이다 (OP 재고 전례).
2. **헤더 이름이 중복이다** — `시작일`·`종료일` 이 두 쌍(수상 기간 / 마케팅 활용 기간)이고
   뒤쪽은 `' 종료일'` 로 앞에 공백까지 있다. **이름이 아니라 위치로** 읽어
   `award_*` 와 `usage_*` 로 가른다. 이름으로 찾으면 두 기간이 조용히 섞인다.
3. **`랭킹/점수` 를 정수로 강제 변환하지 않는다** — `97%`·`-` 가 섞여 있다.
   원문을 `rank_raw` 에 그대로 두고, 깔끔한 정수일 때만 `rank_value` 에 넣어
   정렬·필터에 쓴다. 못 파싱한 행은 **버리지 않고 "순위 미상"** 으로 남긴다
   (성분에서 '미상'을 '미포함'으로 쓴 오답과 같은 함정).
4. **`가능 여부` 를 해석하지 않는다** — 기호(`O`/`△`/`X`/`논의중`/빈칸)를 그대로 보여주고
   `usage_note`(예: *"국문 엠블럼으로 사용 가능, 사용처 화해 검수 필요"*)를 함께 싣는다.
   ⛔ 답변이 "사용 가능합니다" 로 **단정하지 못하게 코드가 막는다.** 프롬프트는 확률이고
   보증은 코드다.

### 3.4 라우팅

`@@수상` (별칭 `어워드` · `awards` · `랭킹정보`), 새 route `awards`.

⛔ **`랭킹` 두 글자를 단독 키워드로 쓰지 않는다.** *"제품 판매 순위"* · *"매출 랭킹"* 은
BigQuery 질문이다. 물류가 `발주` 를 단독으로 쓰지 않고 물류 축 낱말과 튜플(AND)로 건 것과
같이, `랭킹` 은 축 낱말(`수상`·`어워드`·`주최사`·`화해`·`글로우픽`·`쇼피 Top`)과 함께일
때만 켠다.

## 4. 2단계 — PR 이슈 (벡터)

### 4.1 ⛔ 선결 조건 — 지금은 403

`skin1004@skin1004-319714.iam.gserviceaccount.com` 이 PR 시트를 못 읽는다.
코드 문제가 아니다(같은 계정으로 OP 재고 시트는 정상). 소유자
(`haein@skin1004korea.com`)가 **뷰어로 공유**해야 한다. 그전에는 코드를 배포해도
프로덕션이 403이다.

### 4.2 청크

**한 행 = 한 청크.** 800자로 자르면 행사 설명이 중간에서 끊기고, 월 단위로 묶으면
수십 건이 한 벡터에 뭉개져 무엇을 찾아도 같은 조각이 나온다.

임베딩 텍스트는 축을 문장으로 펴서 넣는다 — 축이 텍스트 안에 있어야 "8월 인도네시아
행사" 가 걸린다:

```
[실적] 2024-06 · JBT · 일본
금번 24년 6월 진행된 메가와리에서 앰플 단일 판매량 40,000개 초과 달성 …
```

payload 는 기존 노션 포인트와 같은 모양(검색·인용 코드를 그대로 쓴다):

| 필드 | 값 |
|---|---|
| `team` | **`"PR"` 고정** — ⛔ 여기에 작성팀을 넣으면 `@@PR` 필터가 깨진다. 이 필드는 소속이 아니라 **칸막이**다 |
| `author_team` | 시트 원문 (`JBT`·`GM WEST`·`BOP` …) |
| `issue_month` `category` `region` | `2024-06` · `실적` · `일본` |
| `page_url` | 시트 URL + gid |
| `text` `content_sha256` `chunk_index` | 변경 감지 |

⛔ **팀 표기를 추정하지 않는다.** 시트에 `BOP`·`B2B3` 가 있는데 공식 12팀에도 `TEAM_MAP`
에도 없다. 아는 것만(`GM EAST`·`GM WEST`·`BCM`·`JBT`·`B2B2` 는 노션 어휘와 일치) 한글
팀명을 텍스트에 함께 실어 의미검색이 닿게 하고, **모르는 값은 원문 그대로 두고 자가
점검에 올린다.** 지어내면 조용한 오답이 되고, 버리면 그 행이 사라진다.

`자료`(링크) 열은 임베딩 텍스트에서 뺀다 — URL은 의미검색에 기여하지 않으면서 청크를
오염시킨다. payload 에만 남기고 답변 본문에 싣지 않는다.

### 4.3 ⛔ 소유권 파일을 분리한다 — 177장 삭제 사고의 재발 방지

노션 파이프라인은 **로컬 JSON 에 있는데 노션에 없는 id 를 지운다**:

```python
removed = {pid for pid in set(local_page_map.keys()) - notion_page_ids
           if not str(pid).startswith("teamres-")}
```

이 가드가 없어서 2026-08-25 첫 실행이 남의 포인트 177장을 통째로 지웠다. 지금 방식은
**접두어 denylist** 라 새 주인이 생길 때마다 사람이 기억해야 한다.

PR 포인트는 **`data/pr_vectors.json` 로 소유권 맵을 분리**해 노션 파이프라인 시야에
아예 들어가지 않게 한다. 접두어를 기억할 필요가 없어지고 사고가 구조적으로 재발하지 못한다.

### 4.4 라우팅

`@@PR` (별칭 `pr` · `홍보` · `보도자료` · `프레인`), route `notion`,
`qdrant_agent.TEAM_MAP` 에 `pr`/`홍보`/`보도자료` → `PR`.

⛔ **일반 라우팅 키워드로 `PR` 두 글자를 쓰지 않는다.** 소문자로 보면
`product`·`promotion`·`price`·`approve` 안에 들어 있고, `textmatch.standalone()` 은
앞 글자가 한글일 때만 보므로 **라틴 낱말 안에서는 무력**하다 (물류 `eta`/`meta` 와 같은 함정).
쓰는 것은 `홍보` · `보도자료` · `프레인` · `PR 이슈`(공백 포함) 넷이다.

⛔ 시트의 `구분` 값을 키워드로 쓰지 않는다 — `실적`(매출 질문) · `입점`(거래처 질문) ·
`행사`(프로모션 캘린더)를 가로챈다.

### 4.5 최신성

전체 이력(2024-06~)을 넣으므로 *"요즘 PR 이슈"* 에 2024년 행사가 그럴듯하게 나올 수 있다.
의미검색은 최신성을 모르고, 에러도 나지 않는다.

순위를 조작하지 않고 **공시로 막는다** — `issue_month` 를 청크 텍스트 맨 앞에 세우고
답변이 항목마다 작성월을 적게 한다. 프로모션 캘린더 보유구간·OP 재고 신선도와 같은
규칙이다(사람은 표를 보지 각주를 안 본다).

## 5. 배선

| # | 위치 | 수상/랭킹 | PR |
|---|---|---|---|
| 1 | `orchestrator._DB_REGISTRY` | `@@수상` route `awards` | `@@PR` route `notion` |
| 2 | 적재 모듈 | `app/core/awards.py` | `app/core/pr_issues.py` |
| 3 | 잡 + `EXPECTED_JOBS` | `awards_sync_daily` | `pr_issues_sync_daily` |
| 4 | `qdrant_agent.TEAM_MAP` | — | `pr`/`홍보`/`보도자료` → `PR` |
| 5 | 소유권 파일 | — | `data/pr_vectors.json` (분리) |
| 6 | 라우팅 키워드 | 튜플(AND) | 낱말 4개 |
| 7 | 자가 점검 | §6 | §6 |
| 8 | 골든셋 | 양방향 | 양방향 |

**프론트는 소스 목록을 `/api/datasources` 로 받으므로 키를 하드코딩하지 않는다.**
남는 것은 그룹의 표현뿐이다 (`GROUP_META`/`GROUP_BY_NAME`). 그래서 둘의 처리가 갈린다:

- `@@PR` → 기존 **`Notion`** 그룹. 이미 `GROUP_BY_NAME` 에 있으므로 **프론트 변경 없음**.
- `@@수상` → 새 그룹 **`브랜드 성과`**. ⛔ `chat.js` 의 `GROUP_BY_NAME` 에 **반드시 함께
  넣는다** — 안 넣으면 그 그룹의 소스가 **에러 없이 화면에서 통째로 사라진다**
  (`static_at_sources` 가 잡는다).

## 6. 감시

**공통 원칙** — 0행은 성공이 아니라 **실패**로 기록한다(권한 만료·탭 이름 변경이 정확히
0행으로 온다). 기존 데이터는 지우지 않는다. 상태가 바뀔 때만 알린다.

| 검사 | 무엇을 보나 |
|---|---|
| `awards_sync` / `pr_issues_sync` | 잡 실행 기록 |
| `pr_vectors_present` | `index_team_counts()` 로 `team="PR"` 포인트 수 — **잡이 돌았다는 것과 검색이 된다는 것은 다르다** (CS 캐시에서 배운 구분) |
| `awards_unknown_usage` / `pr_unknown_team` | 새 기호·미등록 팀코드가 조용히 늘어나는 것 |
| `*_sheet_freshness` | 시트 `modifiedTime` vs 마지막 적재 — 시트가 안 바뀐 건지 우리가 못 읽은 건지 가른다 |

`synced_at` 비교 전에 `microsecond=0` — OP 재고에서 방금 넣은 12,166행을 그대로 지우고
'성공' 했던 함정이다.

## 7. 검증

**단위 테스트**
- 헤더 행 탐색(안내문이 늘어도 찾는다) · 중복 헤더를 위치로 가르기
- `랭킹/점수` 파싱(`97%`·`-` 는 미상, 정수만 `rank_value`)
- `가능 여부` 를 문장으로 해석하지 않음
- 행→청크 변환 · 팀 정규화(아는 것만)
- **키워드 충돌 양방향** — `product`·`promotion` 이 PR 을 켜지 않을 것, `매출 랭킹` 이
  `awards` 로 가지 않을 것
- **소유권 파일 분리** — 노션 파이프라인 삭제 대상에 PR id 가 절대 안 들어갈 것 (177장 회귀)

**골든셋 (양방향)**

```
awards_reaches_awards      "화해 어워드 1위 한 제품"      → awards
awards_sales_stays_bq      "제품별 판매 순위 알려줘"       → bigquery
awards_usage_not_asserted  "이 수상 마케팅에 써도 돼?"     → 단정하지 않고 기호·조건 인용
pr_issue_reaches_pr        "8월 PR 이슈 알려줘"           → notion + 작성월 표기
pr_sales_stays_bigquery    "6월 실적 알려줘"              → bigquery
pr_promo_stays_promotion   "8월 행사 일정 알려줘"          → 프로모션 캘린더
```

⚠️ 기대 키워드는 **그 답변에서만 나올 값**으로 쓴다. `실적`·`행사` 같은 일반어는 되묻기
문장에도 들어가 거짓 통과를 만든다. 그리고 **살아 있는 값을 문자열로 얼리지 않고**
`number_near` 를 쓴다 (2026-09-07 문항 4개가 그래서 매일 실패했다).

## 8. 남는 위험

- **PR 의 `구분` 이 실적·입점을 담고 있어 BigQuery 와 의미가 겹친다.** 라우팅 키워드로
  갈랐지만, *"인도네시아 쇼피 1위"* 처럼 물으면 PR 서술과 매출 조회 중 어느 쪽이 맞는지
  **질문만으로는 알 수 없다.** 골든셋으로 감시하되 완전히 없앨 수 없다.
- **수상/랭킹과 PR 의 `실적` 행도 겹친다** — 같은 사실이 두 소스에 있을 수 있다.
  답변이 출처를 밝히게 한다.
- **선결 조건이 사람 손에 있다** — PR 시트 공유 전까지 2단계는 배포해도 403이다.

## 9. 순서

1. 수상/랭킹 적재 + 조회 경로 + 감시 + 회귀 → 배포·검증
2. PR 시트 공유 확인 → PR 벡터 적재 + 라우팅 + 감시 + 회귀 → 배포·검증

⚠️ 배포는 작업트리를 통째로 전송한다. 다른 세션이 진행 중이면 배포 전에 `git log` 로
확인한다 (2026-09-07 실제로 남의 미검증 라우팅 변경이 함께 나갔다).
