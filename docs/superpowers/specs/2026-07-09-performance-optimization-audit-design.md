# 전체 성능 최적화 감사 설계

**Date**: 2026-07-09
**Status**: Approved
**Scope**: 챗봇 응답 속도(SQL 에이전트/오케스트레이터 경로) + 서버 리소스(메모리/CPU) — 정적 코드 감사 기반, 원인 미상 상태에서 시작

---

## 배경

사용자가 프로젝트 전반의 성능 최적화를 요청. 구체적으로 느린 지점을 모르는 상태(원인 미상)이며, 프로파일링/측정부터 시작하기로 결정. 별도 프로파일링 하네스를 새로 구축하기보다(2안), 빠르고 리스크 낮은 정적 코드 감사(1안)로 시작해 구체적 병목을 짚어낸다.

**선행 조사 결과**: 2026-04-20 BigQuery 성능 개선 스펙(`2026-04-20-bigquery-performance-design.md`)에서:
- 방안 B(SQL 파티션 필터 강제, `_enforce_partition_filter`)는 `sql_agent.py`에 **구현 완료**됨.
- 방안 A(조기 SSE 피드백, `status_callback`)는 **미구현** — routes.py/orchestrator.py 어디에도 없음. 체감 응답속도 개선 효과가 크고 리스크가 낮으므로 이번 감사 범위에 포함.

## 감사 대상 & 방법

병렬 Explore 에이전트 4개를 클러스터별로 투입해 "느려질 수 있는 구체적 지점 + 파일:라인"을 보고하도록 지시:

1. **에이전트 경로** (`app/agents/orchestrator.py`, `sql_agent.py`, `cs_agent.py`, `gws_agent.py`, `query_verifier.py`)
   - 순차적으로 실행되는 LLM 호출 중 병렬화 가능한 것
   - 불필요한 재시도/재검증 중복 LLM 호출
   - 대화 이력(컨텍스트) 누적으로 인한 토큰/메모리 증가
   - 조기 SSE 피드백(방안 A) 미구현 확인 및 적용 지점 파악

2. **API/라우팅** (`app/api/routes.py`, `main.py`, `admin_api.py`, `admin_group_api.py`, `auth_api.py`, `conversation_api.py`)
   - async 핸들러 내 blocking I/O (동기 requests, 동기 DB 호출 등)
   - 미들웨어 오버헤드, 요청마다 반복되는 무거운 초기화
   - 인증/RBAC 체크의 중복 DB 조회

3. **DB 레이어** (`app/db/mariadb.py`, 관련 스키마/모델)
   - 커넥션 풀 설정 (크기, 재사용 여부)
   - N+1 쿼리 패턴
   - 인덱스 누락 가능성이 있는 자주 쓰는 쿼리

4. **BigQuery/SQL 실행 경로** (`sql_agent.py`, `query_verifier.py`, `prompts/sql_generator.txt`)
   - SQL 생성-검증-실행 단계의 중복/불필요 LLM 호출
   - 대용량 결과셋 처리 방식(전체 로드 vs 스트리밍/제한)
   - 기존 파티션 필터 강제 로직이 모든 경로에 적용되는지 확인

## 리소스 베이스라인

`pm2 status`로 현재 skin1004-prod의 재시작 카운터(↺)와 메모리 사용량을 감사 시작 전에 기록해 "최적화 전" 기준으로 남긴다.

## 경량 계측 (조건부)

감사에서 특정 단계(LLM 호출, SQL 실행 등)가 의심되면 그 지점에만 `time.perf_counter()` 기반 로그를 추가. 전면적 프로파일링 하네스는 구축하지 않음(범위 밖).

## 수정 우선순위 & 구현

발견 항목을 **영향도(응답속도/메모리 절감폭) × 리스크(운영 중 서비스 영향)**로 분류 → 리스크 낮고 영향도 높은 항목부터 순차 수정.
- 1~2파일 단위 사소한 수정: 메인 루프가 직접 처리
- 여러 파일에 걸친 기계적 반복 수정: Codex에 위임
