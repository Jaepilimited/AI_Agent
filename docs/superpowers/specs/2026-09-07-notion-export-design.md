# 노션 연동 — 출근 브리핑 자동 배송 + 채팅 답변 저장 (2026-09-07)

## 왜

사용자 요청(2026-09-07): *"today 첫 화면에서 확인되는 지표 및 업무 가이드가 너무 유용하여,
노션 개인페이지에 연동하고자 했는데요! (like 잔디 연동)"* — 이어서 *"브리핑 뿐만아니라
다른것들도 요청하면 넣을수 있게"*, 구체화하면 **채팅에서 말로 시켜 그 답변을 노션에 넣는 것**.

잔디 연동이 이미 있고, 그 배관(07:30 생성 · 대기열 · 중복 방지 · 도착 시각 · 절 끄기 ·
자가 점검)이 대부분 그대로 쓰인다. **잔디보다 오히려 단순하다** — 잔디는 WAS·APP 양쪽에서
프록시 403이라 DB_PC 예약작업이 SSH 터널로 꺼내 가는 릴레이가 필요했지만, 노션은
WAS가 `api.notion.com` 에 직접 닿는다 (`qdrant_pipeline_daily` 가 매일 05:00에 부르고 있다).

## 1. 인증 — 쓰기 전용 인테그레이션

- 노션에 내부 인테그레이션 `셀라` 를 새로 만든다. capability 는 **읽기 + 삽입**
  (읽기는 URL 유효성·페이지 제목 확인용), **사용자 정보 없음**.
- 토큰은 `settings.notion_write_token` (`.env` 의 `NOTION_WRITE_TOKEN`).
  - ⛔ **`.env` 는 배포에서 제외된다** — WAS에 직접 넣고 재기동해야 한다.
    코드만 올리면 기능이 조용히 꺼진 채로 돈다 (모델명이 안 바뀌던 그 함정).
  - 값이 비어 있으면 기능 전체가 **꺼진 상태**로 동작한다: 첫 화면에 `노션으로 받기` 가
    보이지 않고, 채팅 관문은 "관리자 설정 전" 안내를 준다. ⛔ 500을 내지 않는다.
- 사용자는 자기 페이지에 `셀라` 연결을 추가한다.
  - ⛔ **노션의 연결은 상위 페이지에 붙고 하위가 전부 상속한다.** 안내 문구는
    *"브리핑 전용 페이지를 하나 만들어 거기에만 연결하세요"* 를 권한다 —
    개인 트리 최상위에 붙이면 그 아래 전부가 이 토큰에 열린다.

## 2. 저장 엔진 — `app/core/notion_export.py`

브리핑과 채팅 답변이 **함께 쓰는 단 하나의 바닥**이다.

### 2.1 URL → page id

`parse_page_url(url) -> str | None`

- 실제 주소에 붙는 것들을 전부 받는다: 한글 슬러그(`.../회의록-24f1a2...`), `?v=`(뷰),
  `?pvs=`, `#블록앵커`.
- 32자 hex 를 뽑아 UUID 형식으로 만든다 (`qdrant_db/notion/client.py::format_uuid` 와 같은 규칙).
- ⛔ **`notion.site`(외부 공개 사이트) 주소는 거절한다.** 인테그레이션으로 쓸 수 없고,
  그대로 두면 404 만 반복한다 (2026-09-04에 학습 쪽에서 이미 겪었다).
- ⛔ 판정 못 하면 `None` 을 주고 **되묻는다.** 추측해서 엉뚱한 페이지에 쓰지 않는다.

### 2.2 마크다운 → 노션 블록

`markdown_to_blocks(text) -> list[dict]`

- 지원: 제목(`#`~`###`) · 문단 · 불릿/번호 목록 · 인용 · 코드펜스 · **표**.
- ⛔ **표는 노션 표 블록으로 만든다.** 매출 표가 코드블록으로 들어가면 노션에서
  정렬도 복사도 안 되는 글자 더미가 된다.
- 노션 API 제약을 코드가 흡수한다 (넘기면 400이 나고, 그건 사용자 눈에 "저장 실패"다):
  - 한 번의 append 는 **블록 100개**까지 → 나눠 보낸다.
  - `rich_text` 하나는 **2,000자**까지 → 쪼갠다.
  - 표는 `table_width` 와 `table_row` 자식이 함께 가야 한다.
- **브리핑 평문도 같은 함수를 통과시킨다.** `work_briefing.render_markdown()` 의 산출물은
  이름과 달리 **평문**이다("잔디는 마크다운을 거의 안 그리므로"). 노션용 렌더러를 따로
  만들면 이 프로젝트가 반복해서 겪은 **사본 갈림**이 된다 — 본문 소스는 하나로 두고,
  변환기가 이모지 머리말(`📅 오늘의 일정 · 3건`)을 소제목으로, 들여쓴 줄을 불릿으로 올린다.

### 2.3 본문 정제 — 잔디 규칙 재사용

`app/core/jandi_briefing`(저장한 보고 절)이 이미 하는 것을 그대로 쓴다:

- ⛔ **`<details>실행된 쿼리</details>` 를 반드시 뺀다** — 노션에서는 평문으로 펼쳐져
  **내부 테이블 경로가 페이지에 남는다**. 노션 페이지는 공유가 쉽다.
- 차트 설정 JSON 코드펜스·후속 제안 칩을 뺀다. 차트를 뺐으면 홀로 남는 `시각화` 제목도 걷는다.
- 차트는 이미 만들어 둔 **글자 막대**(`█`/`░`)로 넣는다. ⛔ 이미지로는 못 넣는다 —
  `public_base_url` 이 내부 전용이라 노션이 가서 받아올 수 없다 (잔디와 같은 벽).

### 2.4 쓰기

`save(page_id, title, text) -> SaveResult`

- 지정 페이지 **아래 자식 페이지**를 만들고 블록을 100개씩 나눠 넣는다.
- 제목: 브리핑은 `2026-09-07 출근 브리핑`, 답변은 **그 질문 첫 줄**(60자 상한).
- 성공하면 **만들어진 페이지 URL** 을 돌려준다 — 답변에 실어 사용자가 눈으로 확인한다.
- ⛔ **실패를 종류별로 갈라 말한다.** "저장하지 못했습니다" 한 줄이면 원인을 모른다:

  | 상황 | 문구의 요지 |
  |---|---|
  | 404 | 그 페이지에 `셀라` 연결이 없거나 URL이 틀렸다 + 연결 방법 |
  | 403 | 워크스페이스가 이 인테그레이션을 막았다 |
  | 400 | 내용이 노션 규격을 벗어났다 (버그다 — WARNING 으로 원문을 남긴다) |
  | 그 밖/타임아웃 | 잠시 뒤 다시 |

  실측상 **404가 압도적으로 흔할 것**이다 (연결을 안 붙이고 URL만 준다).

## 3. 채팅 경로 — 되묻고 URL 받기

### 3.1 관문 위치

`app/core/notion_save.py` 의 `notion_save_intent(query)` 를 **라우터보다 먼저** 건다 —
`orchestrator.route_and_execute`(≈1162행)와 `route_and_stream`(≈1442행)의
`answer_team_country_scope` 관문과 같은 자리, **양쪽 모두**.

⛔ 한쪽만 걸면 경로에 따라 답이 갈린다. 채팅은 스트리밍으로 나간다 — 실사용 경로는
`route_and_stream` 쪽이다 (`answer_check` 를 만들어 놓고 비스트리밍에만 배선해
실트래픽에서 한 번도 돌지 않았던 사고가 있었다).

### 3.2 판정

- **저장 동사 + 노션**이 함께 있을 때만 참: `넣어`·`저장`·`올려`·`보내`·`추가` × `노션`.
- ⛔ 검색과 갈라야 한다 — `노션에서 찾아줘` · `노션에 뭐 있어` · `노션 문서 어디 있어` 는
  **검색이다**. 회귀를 양방향으로 건다.
- ⚠️ 낱말 경계는 `app/core/textmatch` 를 쓴다 (`노션` 은 짧다).

### 3.3 되묻기와 이어받기

- URL이 질문에 없으면 되묻는다. 문구에 **연결 방법을 함께** 적는다
  (`페이지 우상단 ⋯ > 연결 > 셀라 추가`).
- 상태는 **직전 assistant 메시지의 숨은 표식**으로만 이어받는다 —
  `app/reports/clarify.py` 와 같은 방식(base64 마커). 별도 세션 테이블을 두지 않아
  **오래된 요청이 나중의 일반 대화를 가로채지 못한다**.
- 저장 대상은 **그 되묻기 바로 앞의 assistant 메시지**다. 마커에 본문을 담지 않는다(길다).
- ⚠️ 되묻기에 답한 메시지가 URL이 아니면(마음이 바뀐 것) 관문을 놓아주고 평소대로 답한다.
- 같은 대화에서 이미 한 번 저장했으면 **그 URL을 기본 후보로 제시**한다
  (`지난번 그 페이지에 넣을까요?`) — 매번 붙여넣게 하면 두 번째부터 안 쓴다.

### 3.4 브리핑 등록도 이 경로로

`브리핑 매일 노션에 넣어줘` → URL을 되묻고 `user_notion_targets` 에 등록한다.
해지는 첫 화면에서. **첫 화면 설정과 같은 테이블**이라 상태가 갈리지 않는다.

## 4. 브리핑 자동 배송

### 4.1 테이블

```
user_notion_targets(user_id PK, page_url, page_id, enabled, send_at,
                    muted_sections, last_sent_at, last_error, created_at, updated_at)
briefing_notion_outbox(id, user_id, for_date, kind, dedup_key, title, page_id,
                       body MEDIUMTEXT, status, send_after, attempts, last_error,
                       created_at, sent_at, UNIQUE(user_id, dedup_key))
```

- 잔디 테이블(`user_jandi_webhooks` · `briefing_jandi_outbox`)과 **같은 모양**이다.
  dedup 키 규칙도 같다(`briefing:2026-09-07`).
- ⛔ **대기열을 잔디와 합치지 마라.** 잔디 대기열은 DB_PC 릴레이가 `pending()` 으로
  집어간다 — 채널 컬럼만 늘리면 릴레이가 노션 건을 가져가 웹훅으로 쏜다.
- ⚠️ `ensure_tables()` 는 잔디와 같이 CREATE + 마이그레이션 목록으로 둔다
  (이미 만들어진 테이블에는 CREATE 문이 닿지 않는다).

### 4.2 적재와 발송

- 적재는 `personal_briefing._enqueue_jandi` 옆에 `_enqueue_notion` 을 둔다.
  **본문·절 끄기·빈 브리핑 판정은 그대로 재사용**한다
  (`content_sections()` · `render_markdown(muted=...)`).
  - ⛔ 실릴 것을 전부 끈 사람에게 머리말만 보내지 않는다 (잔디와 같은 규칙).
- 발송은 WAS APScheduler 잡 `notion_push_halfhourly`(:05/:35) 가
  `send_after <= now_kst()` 인 것만 꺼내 쓴다.
  - ⛔ `NOW()` 로 비교하지 마라 — DB `time_zone` 이 `SYSTEM` 이다.
    `jandi_briefing.now_kst()` 를 **파라미터로** 넘긴다.
  - ⚠️ `send_after IS NULL` 도 함께 꺼낸다 (즉시 발송분).
- 도착 시각 선택지는 잔디와 같은 창(08:00~18:30, 30분)을 쓰되 **릴레이와 무관**하다 —
  노션은 WAS가 직접 쓰므로 이론상 아무 시각이나 된다. 다만 두 화면이 다른 목록을 보이면
  혼란이라 같은 상수를 쓴다.

### 4.3 API·화면

- `GET/PUT/DELETE /api/personal-briefing/notion` + `POST .../notion/test`
  (잔디 API와 같은 모양, `app/api/notion_briefing_api.py`).
  - PUT 은 **URL을 비워서 보내면 저장된 것을 쓴다** (화면은 주소를 가려서 받으므로,
    시각만 바꾸려는 사람이 되붙일 방법이 없다 — 잔디와 같은 함정).
  - `muted` 를 안 보내는 것과 빈 배열은 **뜻이 다르다** (없으면 "안 바꿈", `[]` 는 "전부 받기").
- 화면은 `personal-briefing.js` 의 `appendJandiSettings` 와 같은 컴포넌트를 재사용하고
  검증 규칙만 갈아 끼운다. ⛔ **절 목록·시각 목록을 프론트에 하드코딩하지 마라** —
  서버가 내려준다 (잔디에서 이미 정한 규칙).

## 5. 조용한 실패 방어

이 프로젝트의 기본 결함 유형이다. 넷을 건다:

1. 자가 점검 `notion_push` — 도착 시각이 **지난** 대기 건이 6시간 넘게 남아 있거나,
   연속 실패가 쌓이면 실패로 올린다. ⚠️ 기다리는 중인 것(18:30을 고른 사람)을
   밀린 것으로 세지 않는다 (매일 뜨는 경고는 곧 아무도 안 읽는다).
2. `EXPECTED_JOBS["notion_push_halfhourly"]` 등록 — 잡이 죽으면 잡힌다.
3. 첫 화면 설정에 **마지막 오류**를 보여준다 (`last_error`). 연결이 끊기면
   그날부터 아무 말 없이 안 가는 것이 기본값이다.
4. 회귀 `tests/test_notion_export.py`:
   - 라우팅 **양방향** (저장 vs 노션 검색)
   - URL 파싱 (슬러그·`?v=`·`notion.site` 거절·쓰레기 입력)
   - 100블록·2,000자 경계, 표 변환
   - `실행된 쿼리` 블록이 본문에서 사라지는지 (**내부 경로 노출**)
   - 실패 문구가 상태코드별로 갈리는지
   - 관문이 **두 경로 모두**에 걸려 있는지 (소스 대조)

## 6. 사생활

- 브리핑에는 메일 제목·요약이 들어간다. **노션 페이지는 공유 한 번이면 새고
  워크스페이스 관리자도 볼 수 있다** — 잔디 개인 토픽과 다른 성격이다.
- 등록 화면에 그 사실을 한 줄 적는다.
- 받을 절의 **기본값은 잔디와 같게(전부 켜짐)** 둔다 (사용자 승인, 2026-09-07).
  여기서 기본을 다르게 하면 "잔디엔 오는데 노션엔 안 온다" 가 된다.
- 저장 URL은 화면에 되돌릴 때 **가린다** (잔디 웹훅과 같은 규칙).

## 안 하는 것 (YAGNI)

- 노션 OAuth — https 회신 URL 벽. 필요해지면 그때.
- 노션 데이터베이스 자동 생성 — 자식 페이지로 충분하다.
- 이미지 차트 — 내부망 URL이라 노션이 못 가져온다.
- 잔디 대기열과의 통합 — 소비자가 다르다.

## 미확정 / 위험

- **워크스페이스 정책이 새 인테그레이션을 막을 수 있다.** 노션 관리자가
  멤버의 연결 추가를 제한해 두었으면 각자 붙일 수 없다 — 착수 직후 실제 페이지
  하나로 확인한다.
- **표 변환의 실물 확인이 필요하다.** 노션 표 블록은 규격이 까다로워
  400을 내기 쉽다. 실제 매출 답변 하나를 넣어 눈으로 본다.
- 되묻기 관문이 기존 라우팅을 가릴 위험 — 회귀를 양방향으로 걸어 막는다.

5. `app/core/notion_briefing.py` (테이블·대기열)

8. `app/api/notion_briefing_api.py` + `main.py` 라우터 등록
9. `personal-briefing.js` `노션으로 받기` + `style.css`
10. `self_check` `notion_push`
11. `tests/test_notion_export.py`
