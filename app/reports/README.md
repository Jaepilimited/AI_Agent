# 보고서 파이프라인

`매출분석/cost_efficiency/` 의 일회성 파이프라인을 재현 가능한 스펙으로 옮긴 것.
질문 하나로 완성 보고서를 내는 것이 아니라, **사람이 검토할 수 있는 초안**을 만든다.

## 두 갈래 — 고정 스펙과 동적 조립

| | 고정 스펙 (`specs/*.py`) | 동적 조립 (`planner`+`blocks`) |
|---|---|---|
| 언제 | 손으로 검증한 깊은 분석 (집계 계약·시뮬레이션) | 질문에 맞춰 넓게 |
| 예 | FOC·바우처 비용 효율화 | "2026년 일본 매출 보고서" |
| 조합 | 고정 | 질문마다 다름 |

`registry.route()` 가 고른다. **고정 스펙이 있으면 그쪽이 이긴다** — 검증된 분석을
얕은 것으로 덮어쓰지 않기 위해서다.

### 동적 조립이 자유로우면서도 안전한 이유

1. **`semantic.py` 가 SQL 을 만든다.** 플래너(LLM)는 "어떤 지표를 어떤 축으로"만 고르고,
   그 조합에서 SQL 은 결정적으로 생성된다. 조합이 유한하고 전부 검증돼 있다
2. **어휘 밖은 버린다.** 모르는 지표·축·블록이 계획에 나오면 그 절을 떨어뜨리고
   `planner_dropped` 로 **로그를 남긴다** (조용히 버리면 품질 저하를 못 본다)
3. **finding 을 LLM 이 쓰지 않는다.** "1위가 전체의 X%", "증가분의 Y%를 상위 3곳이 만들었다" —
   전부 `blocks.py` 의 규칙이 숫자에서 뽑는다. 제목·도입부에 숫자가 있으면 버린다
4. **필터는 결정적으로 뽑는다.** "일본 매출 보고서"의 '일본'을 LLM 에 맡기지 않는다
   (`registry.extract_filters`). 놓치면 질문에 답하지 않은 전사 보고서가 나온다.
   뽑은 필터는 **모든 절에 강제**된다
5. LLM 이 죽어도 `planner.default_plan()` 으로 보고서는 나온다

## 사용자는 채팅에서 질문으로 받는다

> "SK FOC 바우처 비용 효율화 보고서 만들어줘" → 요약 4줄 + `[보고서 열기]` 링크 (5초)

### 언제 만들어지는가 (2026-08-13 규칙)

보고서는 조회 8~12회에 10~30초가 드는 **특수 경로**다. 둘 중 하나여야 만든다:

1. **`@@보고서`** 로 데이터소스를 지정 — 이 경우 문구를 보지 않는다
2. 질문에 **"보고서"·"리포트"·"report"** 라고 적음

⛔ 예전 신호어 "분석해줘·정리해줘·종합·진단·심층·브리핑"은 뺐다. 평범한 조회에도 흔해서
의도치 않은 보고서가 계속 생겼다 (하루에 12건).

### 이렇게 물으면 보고서가 나온다

필터는 **결정적으로** 뽑히므로(`registry.extract_filters`), 아래 굵은 부분이 그대로 모든 절에 걸린다.

| 질문 | 걸리는 필터 |
|---|---|
| **2026년 일본** 매출 보고서 만들어줘 | 국가=일본 |
| **일본 B2C** 매출 보고서 — 달마다 오르내리는 원인 위주로 | 국가=일본 · 영업유형=B2C (+프로모션 절) |
| **우마** 브랜드 매출 보고서 만들어줘 | 브랜드=UM |
| **스킨천사** 상반기 매출 보고서 | 브랜드=SK+CBT |
| **좀비뷰티** 매출 보고서 | 브랜드=SK · 라인=ZB |
| **중국사업팀** 상반기 실적 보고서 | 팀=CBT (국가는 안 건다) |
| **동남아** 채널별 매출 보고서 만들어줘 | 권역=동남아시아 (`Continent2`) |
| **미국 B2C** 채널별 매출 보고서 | 국가=미국 · 영업유형=B2C |
| **SK FOC 바우처 비용 효율화** 보고서 만들어줘 | 고정 스펙 `cost_efficiency` |
| `@@보고서` 2026년 일본 b2c 매출 | 지정이므로 '보고서'라는 말이 없어도 만든다 |

- 기간을 안 쓰면 **직전에 끝난 반기**다. "상반기"·"2026년"처럼 적으면 그대로 따른다
- ⚠️ **UM·CBT 는 제품별 절이 나오지 않는다** — 제품명이 100% 비어 있다(2026-08-13 실측).
  안 팔린 게 아니라 적재가 없는 것이라, 보고서가 그 사실을 본문에 공시한다
- ⛔ **"우마 매출 분석해줘" 는 보고서가 아니다** — '보고서'라고 적어야 한다

- 판정은 `registry.match()` — **보고서 신호어** + **주제어**가
  둘 다 있어야 한다. "FOC 얼마야?" 같은 단순 조회를 보고서로 만들지 않는다
- 기간은 `registry.parse_period()` 가 결정적으로 뽑는다. 명시가 없으면 **직전에 끝난 반기**다 —
  진행 중인 반기를 기본으로 잡으면 두 달치로 반기 비율을 내고 그걸 반기 실적처럼 읽는다
- ⛔ **열람은 만든 사람 + 만든 사람이 지목한 사람만.** admin 도 예외가 아니다 (2026-08-12 결정).
  원가·마진·거래처별 FOC율이 들어가므로 매출 질문과 같은 수준으로 열지 않는다.
  판정은 `store.get_for_user()` **한 곳에서만** 한다 — 흩으면 한 곳만 고치고 뚫린다
- 없는 것과 남의 것을 구분해 알려주지 않는다 (둘 다 404)
- 같은 스펙·기간이면 payload 를 재사용하되 **요청자 본인의 행을 새로 만든다.**
  남의 행을 그대로 돌려주면 열람 권한이 무너진다

### 공유 (2026-08-13)

**사람을 지목한다.** 링크를 아는 사람이 다 열 수 있는 방식은 만들지 않았다 — 잔디·메일로
한 번 새면 회수할 수단이 없기 때문이다. 대신 URL 은 그대로 붙여도 된다: 지목된 사람만
열리고 나머지는 404 를 본다. 누구에게 갔는지는 언제든 보고 되돌릴 수 있다.

| | 어디서 | 판정 |
|---|---|---|
| 열람 | `store.get_for_user` | 소유 **또는** 공유 — 한 SQL 에서 함께 본다 |
| 공유 걸기·해제 | `store.share_add` / `share_remove` | 소유자 여부를 **SQL 안에서** 확인한다 |
| 대상 검색 | `store.search_share_targets` | 가입한 사용자만 · 2글자 미만은 조회하지 않는다 |

- ⛔ 공유를 거는 쪽도 **SQL 안에서** 소유자를 확인한다 (`INSERT ... SELECT ... WHERE
  r.user_id = %s`). 파이썬에서 먼저 확인하고 나중에 INSERT 하면 확인을 빠뜨린 호출부가 생긴다
- 대상은 **가입한 사용자만**이다. FI 는 미가입자에게 미리 부여해두지만([[CLAUDE.md]]),
  공유는 지금 보여주려고 누르는 동작이라 열 수 없는 사람을 목록에 올리면 공유한 줄 알게 된다
- ⚠️ 공유 막대(`share_ui.py`)는 **저장본에 굽지 않고 응답마다 끼운다.** 파일 하나를 여러
  사람이 열기 때문에, 구워 넣으면 보는 사람마다 달라야 할 것이 만든 사람 기준으로 굳는다.
  인쇄·PDF 에서는 빠진다
- ⚠️ `GET /api/reports/share-targets` 는 `/{report_id}` **위에** 둔다 — 아래 두면 422

## 보고서의 뼈대 — 맨 앞 절이 논지를 말한다 (2026-08-13)

절을 나열하기만 하면 **표 모음**이지 분석이 아니다. 맨 앞에 `요약과 해석` 절 하나를
두고 역할을 나눈다.

| 부분 | 누가 쓰나 | 무엇을 |
|---|---|---|
| **사실** (≤3줄, 굵게) | `dynamic._headline()` — 규칙 | 무엇이 얼마인가 (규모·성장·대상 vs 나머지·데이터 결함) |
| **해석** (≤8줄) | `insight.py` — **LLM** | 왜 그런가·무엇이 걸리는가 |
| **다음 할 일** (≤3건) | `insight.py` — **LLM** | 무엇을 확인·실행할까 |

- ⚠️ **요약을 길게 쓰지 마라.** 처음엔 추세·기여도·프로모션까지 여섯 줄을 담았더니
  바로 아래 해석과 같은 얘기를 두 번 했다. 요약은 "무엇이 얼마인가"에서 멈춘다
- ⛔ **겹침은 프롬프트가 아니라 후처리로 막는다.** 이미 적힌 요약을 LLM 에 넘기고,
  돌아온 문장의 수치 집합이 요약 한 줄에 **완전히 포함되고 새 수치가 없으면 버린다**
  (`_echoes`)

### `insight.py` — 이 파이프라인에서 **유일하게 LLM 이 문장을 쓰는 곳**

규칙으로는 "그래서 무엇을 해야 하나"를 쓸 수 없어서 연 예외다. 대신 **숫자는 만들지
못하게** 한다 — 문장 속 모든 수치를 조회 결과와 대조해 하나라도 없으면 그 문장을 버린다.

- ⛔ 검증은 **프롬프트 지시가 아니라 후처리**다 (국가·팀 리터럴 교정과 같은 이유)
- ⛔ **잘린 문장도 버린다.** `generate_json` 이 토큰 상한에 걸리면 `repair_json` 이
  괄호를 닫아 **잘림이 정상 JSON 처럼 보인다** — 실제로 중간에서 끊긴 문장이 실렸다.
  `max_output_tokens=8192` 로 올리고 끝맺음 없는 문장을 거른다
- 버린 문장은 `insight_dropped_unverified` 로 **WARNING** 에 남긴다. 조용히 버리면
  "왜 짧지"를 알 수 없다
- LLM 이 죽어도 보고서는 나온다 — 사실 요약은 규칙이 쓰기 때문이다

### `versus` — 대상 vs 나머지

필터는 **모든 절에 AND 로** 걸리므로, 그대로 두면 비교 대상이 존재할 수 없다.
"일본이 다른 나라와 뭐가 달랐나"를 물어도 일본만 나온다.

- 이 절만 **주 필터 하나를 빼고** 한 번 더 조회해 `나머지 = 전체 − 대상` 을 만든다
- 주 필터 우선순위: 국가 → 권역 → 대륙 → 팀 → 브랜드
- 남은 필터(영업유형 등)는 양쪽에 똑같이 건다 — 일본 B2C 는 **일본 외 B2C** 와 견준다
- 좁힌 대상이 없으면 절을 만들지 않는다 (조회도 하지 않는다)

### 마케팅 × 매출 × 프로모션 — 섞을 수 있는 축은 넷뿐

광고(`integrated_ad`)와 매출은 **국가·팀·월·분기**에서만 만난다. 광고 테이블에
채널·브랜드·제품이 없기 때문이다. 그 넷 위에서 `ratio` 절이 두 조회를 축 키로 나눠
ROAS 를 만든다 — SQL 조인이 아니라 파이썬에서 나눈다.

- ⛔ **ROAS 0 을 "가장 낮은 곳"으로 쓰지 않는다.** 전환 추적이 없으면 0 으로 들어온다 —
  매출이 없다는 뜻이 아니다. 분자가 0인 행은 **순위에서 빼고 그 사실을 본문에 적는다**
  (원가 미적재 브랜드도 같은 함정이다)
- ⛔ 전환매출은 **광고 플랫폼이 스스로 집계한 값**이라 `Sales1_R` 과 다르다. 서로 다른
  테이블을 나눈 비율에는 그 사실을 `note` 로 붙인다 — 방향만 읽으라는 뜻이다
- 프로모션 캘린더는 **왜 그 달에 튀었는가**를 맡는다. 매출의 톱니 모양에서 주기를
  추정하지 않는다 (그건 실적 테이블이 모르는 사실이다)

### 상관과 외부 맥락 — 계산한 것과 아닌 것을 섞지 않는다

| | `correlation` | `external` |
|---|---|---|
| 출처 | 조회한 두 시계열 | 구글 검색 |
| 내는 것 | 피어슨 계수 + 1개월 지연 | 그 달에 있었던 일 (문장) |
| 주장 | 상관까지. 인과는 명시적으로 부정 | **아무것도 주장하지 않는다** |

- `correlation` 은 점이 6개 미만이면 만들지 않는다. "상관은 인과가 아니다"를 발견에 항상 넣는다
- ⛔ **`external` 은 상관계수를 내지 않는다.** 검색은 문장을 줄 뿐 시계열을 주지 않으므로
  계수를 낼 근거가 없다. LLM 이 "기온과 매출 상관 0.72"를 쓰면 계산이 아니라 창작이고,
  **통계처럼 생겨서 가장 잘 믿긴다.** 진짜 날씨 상관이 필요하면 기온을 적재하면 되고,
  그때는 `correlation` 이 그대로 계산한다
- 코드가 버리는 것 셋: **숫자**(연월만 허용) · **인과 표현** · **우리 실적 언급**
- `insight` 의 사실 묶음에서 **제외**한다 — 검증 안 된 문장이 해석의 근거가 되면 끝이다

### 차트

- ⛔ **바닥은 0이다.** 최솟값을 바닥에 붙이면 면적이 거짓말을 한다 (최저 6.6억이 0으로 보였다)
- ⛔ **축선과 축 제목이 있어야 차트다.** 눈금 숫자만 떠 있으면 표의 장식이다.
  축 제목은 payload 의 컬럼 라벨에서 가져와 차트와 표가 같은 말을 쓰게 한다
- ⚠️ y축 제목은 **맨 왼쪽 고정**. `padL` 기준으로 잡으면 눈금·범주 라벨과 겹친다
  (라벨 길이가 데이터마다 달라 여백을 계산으로 못 맞춘다)
- 범주형 절은 **가로 막대**(이름이 길다), 기간 추세는 **세로 막대**(x가 시간이다)
- ⚠️ **그리는 값 기준으로 정렬해 자른다.** 표 순서(매출순)대로 자르면 가장 크게
  줄어든 항목이 잘려 나간다
- ⚠️ 절마다 **무엇을 그릴지**(`chart_key`)를 정한다. compare 를 value 로 그렸더니
  바로 앞 구성 절과 똑같은 그림이 두 번 나왔다 — 그 절은 `delta` 를 그려야 한다

### 한국어 문장

- `blocks._josa()` 로 받침에 맞는 조사를 붙인다. "일본**는**", "55.1억**가**" 처럼
  틀리면 자동 생성 티가 난다. 한글 받침·숫자 읽기(0·1·3·6·7·8은 받침)·영문 어미 처리
- 발견 문장은 **평문으로 렌더**된다(HTML 주입 방지) — 마크다운을 쓰면 별표가 그대로 보인다

## CLI

```
python scripts/build_report.py cost_efficiency              # 조회 → payload → HTML → 검증 SQL
python scripts/build_report.py cost_efficiency --lint-only  # 조회 없이 템플릿만 점검 (빠름)
python scripts/render_report_pdf.py docs/reports/cost_efficiency.html
```

산출물은 `docs/reports/<스펙>.{html,payload.json,verify.sql,pdf}`.
채팅으로 만든 것은 `data/reports/<id>.html` + `reports` 테이블.

|---|---|---|
| 스펙 | `specs/*.py` | 무엇을 조회·점검·계산할지 **선언**만 한다 |
| 엔진 | `engine.py` | 조회 → 게이트 → 파생. `validate_sql()` 을 그대로 통과시킨다 |
| 렌더 | `render.py` | payload + 템플릿 → HTML. 슬롯 린터를 강제한다 |
| 템플릿 | `templates/*.html` | 서술과 레이아웃. **숫자는 슬롯으로만** |

## 지켜야 할 규칙

- **숫자는 코드가, 문장은 템플릿이 만든다.** LLM 이 숫자를 쓰는 경로를 두지 않는다.
  ([[CLAUDE.md]] 의 "성분 SQL 을 LLM 에 맡기지 마라" 와 같은 사상)
- **본문에 숫자 리터럴을 남기지 마라.** `render.lint_template()` 이 잡는다.
  기간 표기("2026 상반기")까지 파라미터로 넣어 `allow_literals` 를 비워둔 이유다.
  도메인 용어(B2B·B2C)만 예외로 허용한다
- **파생 지표는 SQL 이 아니라 파이썬에서.** 비율·나눗셈을 생성 SQL 에 맡기면 검산할 수 없다
- ⚠️ **반올림한 값으로 `HAVING` 을 걸지 마라.** 억 단위로 반올림한 뒤 `> 0` 으로 거르면
  소액 건이 통째로 사라진다 — 거래처 수가 420 → 122 로 줄었던 실제 사고(2026-08-12).
  **필터·비율은 원값으로, 반올림은 표시할 때만**
- **모든 fact 에 `expect` 를 달아라.** `verify.sql` 에 기대값 주석으로 나가 사람이 검산한다
- 템플릿의 `/*__PAYLOAD__*/` 는 `<script type="application/json">` 안에 둔다.
  JS 식 자리에 두면 치환 후 문법 오류가 난다 (실제로 겪음)
- ⚠️ **캐시 해시는 '요청 시점' 파라미터로 만든다.** 게이트가 채널을 제외하면 2회차
  파라미터가 달라지는데, 최종 파라미터로 해시를 만들면 다음 요청과 영영 어긋나
  캐시가 절대 히트하지 않는다 (2026-08-12 실측 — 히트한 줄 알았는데 재조회하고 있었다)
- ⚠️ **스트리밍에서 진행 문구를 `("chunk", …)` 로 보내지 마라.** `routes.py` 가
  `streamed_live` 를 세워 뒤따르는 `("done", 본문)` 을 통째로 버린다.
  소비부가 아는 이벤트는 `source`·`chunk`·`done` 셋뿐이다
- ⛔ 조회 병렬화에 `with ThreadPoolExecutor` 를 쓰지 마라 (CLAUDE.md 금지 규칙).
  `shutdown(wait=False)` 를 `finally` 에 둔다
- ⚠️ **블록의 기간을 헷갈리지 마라.** 구성·순위·교차·총량은 `focus_start/end`(중점 반기),
  추세만 `start/end`(전체 구간)다. 섞으면 18개월 합계를 반기 실적으로 읽는다 —
  실제로 전년 대비가 +303%로 나왔었다 (2026-08-12)
- ⚠️ **테이블마다 컬럼명이 다른 축이 있다.** 제품은 SALES 에서 `` `SET` ``,
  Product 테이블에서 `Product`. `Dimension.expr_by_table` 로 나눈다.
  그리고 `SET` 은 BigQuery 예약어라 백틱이 필수다
- ⚠️ **테스트는 서버 인터프리터로 돌려라** —
  `C:\Users\DB_PC\AppData\Local\Programs\Python\Python311\python.exe`.
  PATH 의 `python` 은 다른 venv 라 `google.genai`·`anthropic` 이 없어
  플래너가 조용히 기본 계획으로 떨어진다 (그러면 모든 보고서가 똑같이 나온다)

## 품질 게이트가 이 파이프라인의 핵심이다

쓰레기 컬럼을 포함한 채 **그럴듯한 비율**을 내는 것이 가장 위험한 실패다 — 조용하기 때문이다.
게이트는 보고서를 멈추지 않고, 제외 사실과 그 영향을 payload 에 남겨 본문에 공시한다.
`blocking=True` 는 집계 계약처럼 "깨지면 모든 수치가 틀리는" 검사에만 쓴다.

실제로 자동 게이트가 수작업 보고서보다 채널 하나를 더 잡았다 (`SK_B2C_sabangnet`).
